# Schedule Skills, Compute Keys, Verify Everything

The FSRS Problem-Solving & Toishi is built on the best-supported findings in learning science. Retrieval practice, spacing and interleaving all have math-specific classroom evidence, including a preregistered trial in which interleaved review beat blocked review 60.7% to 37.6% a month later. Its central technical bet has never been validated, though: scheduling *skills* with FSRS and drawing a fresh problem for each review. FSRS should be treated as an approximation that the app checks against its own logs. Three things decide whether the app works. The first is an acquisition phase, so no skill enters cold review before it has been learned: in studies without feedback, retrieval at or below 50% initial success produced essentially zero benefit. The second is an honest rating derived automatically from correctness, hints and attempts rather than from self-report. The third is an answer-key pipeline in which code computes the key wherever possible, because model-written answers to synthetic problems were wrong 30.5% of the time and models flag broken problems only about a third of the time when not prompted to look. No published method can prove "zero errors." The app can get close with templates, independent derivations, an adversarial check that each problem is well-posed, a rule that disputed items are dropped, and an in-app button that pulls a reported problem from use. The tentative stack (Python, PySide6, SQLite, py-fsrs 6.3.2, SymPy, KaTeX) holds up, with four traps: PySide6 6.12 moved QtWebEngine into a separate package and requires macOS 14+, SymPy's text parser calls `eval`, py-fsrs measures elapsed time in whole days and returns default parameters until it has 512 reviews, and KaTeX only displays math, so typed input needs MathLive. Two earlier positions need revisiting. Newer Anki guidance reverses the earlier triage advice: when the count is short, defer the reviews *least* likely to be recalled, not the most. And the research budgets workload in time rather than item counts, which the question-count design can absorb by logging time per item and showing projected minutes. On content, OpenStax relicensed its algebra, physics, chemistry and statistics books to CC BY-NC-SA in March 2026. The WeBWorK library holds thousands of files tagged to commercial textbooks, including 7,581 tagged to Stewart. Many of those tags are only cross-references, but files that copy a numbered textbook exercise should be excluded under the no-copyrighted-exercises rule. Publishing the app would also trigger attribution, ShareAlike, NonCommercial and Japanese reporting obligations that a private build never triggers.

## Seven decisions to settle before the first commit

Most of the user's decisions survive the research intact. Two do not, and the rest need specific settings. The table summarizes where each one stands. Sections 2 through 7 give the evidence.

| Decision | Current position | What the research found | Recommendation |
|---|---|---|---|
| Daily workload | User-chosen question count | Time per problem varies widely, interleaved items take longer, and practitioners budget in minutes | Keep the count as the control, log duration from day one, show projected minutes, offer an optional minutes cap |
| Backlog triage | New material waits first, then the most-recallable reviews wait | New-first is confirmed; for reviews, FSRS-era Anki guidance does the most-recallable first | Keep new-first, then switch review deferral to lowest retrievability first, with guards for prerequisites and exams |
| Scheduler | FSRS per skill, fresh problem per review | FSRS-6 is current; no study validates it for skills; default parameters were fit on flashcards | Pin py-fsrs 6.3.2 behind an adapter, gate updates by problem difficulty, log calibration, re-fit after 512 reviews |
| Stack | Python, PySide6, SQLite, py-fsrs, SymPy, KaTeX | Confirmed as the simplest option; Tauri or Electron would still need a Python sidecar for SymPy | Keep it; add MathLive; use Python 3.12 or 3.13; package with PyInstaller onedir |
| Answer keys | Zero errors, token-efficient pipeline | Zero cannot be proven; ill-posed problems outnumber wrong arithmetic | Compute keys with templates first, accept fixed problems by provenance, drop disputes, add an in-app report button |
| Content policy | Open or permitted only; originals in Gaokao/CSAT style; permitted Japanese exams | OpenStax is now BY-NC-SA; OPL mirrors commercial textbooks; Tokyo, Kyoto, Kyushu and Shinshu allow reuse with conditions | Exclude textbook-mirror OPL files, track a license per item, send originals through the strictest acceptance path |
| Distribution | Anyone could download their own copy | Publishing triggers CC, GFDL, LGPL and Japanese reporting duties; unsigned builds show OS warnings | Store attribution metadata now; decide about publishing before the first public release |

### The earlier triage advice runs opposite to current Anki guidance

Earlier in this conversation, the assistant suggested that when more is due than the daily count, new material waits first, and then the reviews least likely to have been forgotten wait. The first half matches Anki's documentation: "Continuing to introduce new cards when you're already behind can make the backlog worse" ([Anki manual](https://docs.ankiweb.net/deck-options.html)). The second half means doing the lowest-retrievability reviews first. That is the old "relative overdueness" order, which Anki now calls "Ascending retrievability," and the manual still lists it for backlogs ([Anki manual](https://docs.ankiweb.net/deck-options.html)). Newer guidance from the FSRS era reverses it. Anki 24.11 added a **descending retrievability** sort and said simulations favor it when there is a backlog ([Anki 24.11 notes](https://newreleases.io/project/github/ankitects/anki/release/24.11)). A 2026 forum answer calls descending retrievability "the order which is usually recommended," because "you will be sacrificing some cards that already have lower R in order to rescue cards that still have higher R" ([Anki forum](https://forums.ankiweb.net/t/a-situation-in-which-descending-retrievability-may-not-be-the-most-efficient-review-sort-order/68947)). Anki 26.05 then made it a "pure R sort" ([Anki 26.05](https://github.com/ankitects/anki/releases/tag/26.05)). A simulation by FSRS's author, relayed on the forum, found that with a **limited** daily count, "Difficulty Ascending performed best, with Retrievability Descending second." With unlimited reviews, the order did not matter ([Anki forum](https://forums.ankiweb.net/t/ordering-request-reverse-relative-overdueness/50051)).

The logic carries over to problem skills, and arguably more strongly. A low-retrievability skill is probably already gone. Spending a scarce slot on it buys a likely lapse that relearning must repair anyway. A skill still at high retrievability, reviewed now, succeeds and multiplies its stability; postponed, it slides toward forgetting. Failed problems also cost far more time than failed flashcards. The cost of waiting also depends heavily on stability. At R ≈ 0.90, one more day of delay costs about 0.030 retrievability for a skill with 2-day stability, 0.0067 at 10 days, and 0.0014 at 50 days (computed from the FSRS-6 forgetting curve in [py-fsrs](https://raw.githubusercontent.com/open-spaced-repetition/py-fsrs/main/fsrs/scheduler.py)). A forum user has proposed sorting by exactly this daily loss (R_today − R_tomorrow), but no simulation or developer response exists for it ([Anki forum](https://forums.ankiweb.net/t/sorting-order-by-today-minus-tomorrow-retrievability-difference/70007)).

The evidence has limits. No source publishes the simulation numbers, every simulation used flashcards, and none models a prerequisite graph. In this app, a forgotten foundational skill blocks new learning and corrupts diagnosis of advanced errors, which flashcards never do. The research notes disagree on this point: one researcher's synthesis proposed low-R-first weighted by exam proximity and dependents, while the scheduling evidence points the other way. The Anki evidence is more specific, so the recommended default is as follows. Defer new skills first. Then do reviews in descending retrievability, computed from fractional days. Apply three overrides: skills that are prerequisites of anything currently being learned or recently failed move to the front; exam-tagged skills inside an exam window move to the front; and no skill waits more than a fixed number of days (a design choice). Implement triage as a pluggable policy and log which policy ran, so the user's own data can compare policies later. A backlog above about twice the daily count for more than a week should prompt the user to raise the count or take a short re-placement check rather than grind. This is Math Academy's "new diagnostic after a break" idea ([Skycak, FIRe](https://www.justinmath.com/individualized-spaced-repetition-in-hierarchical-knowledge-structures/)).

### A question count works if the app also counts minutes

The research consistently budgets time, not items. Teachers reported that interleaved assignments took longer ([Matuschak on Rohrer et al. 2020](https://notes.andymatuschak.org/zHvJf88XUgLPMhdTigkoiUR)), varied retrieval items take the most time ([Learning Scientists on Cao & Carvalho 2026](https://www.learningscientists.org/blog/2026/6/18-1)), and Math Academy calibrates its points to roughly one minute of focused work, with **50–60 minutes a day** as the practical sustainable ceiling ([Skycak](https://justinmath.com/what-is-the-highest-sustainable-daily-xp-on-math-academy/)). A count is concrete, matches how homework is assigned, and avoids watching the clock. Its weakness is drift. Fifteen questions can take 20 minutes on a day of derivative drills and 90 on a day of optimization word problems plus two new-skill lessons, and the scheduler's own choices (harder tiers, synthesis problems, lessons) silently inflate the time. FSRS's optimal-retention calculation also needs per-review durations ([py-fsrs optimizer](https://raw.githubusercontent.com/open-spaced-repetition/py-fsrs/main/fsrs/optimizer.py)).

The count can stay as the user's control if the app defines what one question is. My recommendation: each graded attempt is one question, and a new-skill lesson (worked example plus acquisition problems) uses a fixed number of slots. The app should record time on every attempt from the first day and show "15 questions, about 45 minutes" from per-skill median times. It should gate new skills on the projected 7-day count. An optional minutes cap can take precedence when set. Same-day reinforcement after a miss also uses slots, which is acceptable because the evidence argues for keeping it short (Section 2).

## Retrieval, spacing and interleaving pay off only after a skill is learned

### The core loop has strong, math-specific support

Attempting a problem before seeing its solution is retrieval practice. A meta-analysis of 222 classroom studies found **g = 0.499** overall and **g = 0.433 for mathematics and statistics**. Rephrased questions benefited at least as much as identical ones (0.558 vs 0.512), but material that was never tested benefited less (0.321) ([Yang et al. 2021](https://gwern.net/docs/spacedrepetition/2021-yang.pdf)). That validates drawing a fresh problem per skill, and it sets a requirement: each skill's problem pool has to span the whole range of problems an exam could ask, not near-clones of one template. Interleaving has the strongest single result. A preregistered cluster RCT with 787 students found **d = 0.83** about a month later, and every teacher saw a positive effect ([Rohrer et al. 2020](https://Www.Gwern.net/doc/psychology/spaced-repetition/2019-rohrer.pdf)). A college physics replication found median improvements of 50% and 125% on novel problems ([Samani & Pan 2021](https://doaj.org/article/da1dfb08ef7d4cd7a757a8dad0716c75)). Across domains the effect is smaller: g = 0.42 overall, 0.34 for math, and about 0.29 after a publication-bias correction ([Brunmair & Richter 2019](https://www.psychologie.uni-wuerzburg.de/fileadmin/06020400/2019/Brunmair_Richter_in_press__2019_META-ANALYSIS_OF_INTERLEAVED_LEARNING.pdf)). For spacing, college math classrooms show modest but durable gains. In engineering precalculus, spaced objectives scored 0.59 versus 0.54 a month after the final, "equivalent to half a letter grade," while doubling the number of quiz questions had no effect ([Hopkins et al. 2018](https://peer.asee.org/29900.pdf)). Spacing a fixed set of college math problems produced 74% versus 49% at one week, and doubling massed practice did nothing ([Rohrer & Taylor 2007](https://www.Gwern.net/doc/psychology/spaced-repetition/2007-rohrer.pdf)). Set expectations accordingly: roughly five percentage points per skill on delayed tests, compounding over years of use. One university study found no spacing effect for permutation procedures ([Ebersbach & Barzagar Nazari 2020](https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2020.00811/pdf)), and spacing benefits shrink for complex tasks ([Donovan & Radosevich 1999](https://www.gwern.net/docs/spaced-repetition/1999-donovan.pdf)).

### Cold retrieval before mastery wastes the attempt

The biggest learning-science risk is sending a skill into review before it is learned. In studies without feedback, initial test performance at or below 50% produced **g = 0.03**, against 0.56 above 75% ([Rowland 2014](https://courseware.epfl.ch/assets/courseware/v1/fdde2f0aa590bf3b1324077a6bf1540c/asset-v1%3AEPFL%2BDEMO%2B2020%2Btype%40asset%2Bblock/Rowland2014-meta-analysis.pdf)). For novices, studying worked examples beats unguided problem solving in math (g = 0.43), but that advantage reverses as expertise grows ([Barbieri et al.](https://www.cehd.udel.edu/wp-content/uploads/2022/02/Worked-Examples-Meta-Poster_022722_SC.pdf); [worked-example effect](https://en.wikipedia.org/wiki/Worked-example_effect)). The classroom interleaving studies themselves placed **the first four problems of each new skill as a block** right after the tutorial ([Rohrer, Dedrick & Stershic 2015](https://Www.Gwern.net/doc/psychology/spaced-repetition/2014-rohrer-2.pdf)). Researchers recommend at least two-thirds of practice be spaced or interleaved, with "at least some blocked practice" at first exposure ([Rohrer & Hartwig](https://www.unh.edu/teaching-learning-resource-hub/sites/default/files/media/2023-06/itow-spaced-and-interleaved-mathematics-practice-rohrer-hartwig.pdf)).

New skills therefore need an acquisition phase in the queue. The phase runs: a worked example with labeled steps, a second varied example or a faded problem, then fresh problems until **2–3 are correct in a row** without hints. Math Academy uses two in a row ([Math Academy](https://mathacademy.com/how-it-works)). In one data-mining study, three in a row predicted the next problems well and five predicted transfer better ([EDM 2015](https://www.educationaldatamining.org/EDM2015/proceedings/poster630-631.pdf)). Successive-relearning research recommends three correct during initial learning, then one correct in each of at least three spaced sessions. That spaced version produced "more than twice as much" recall as three correct answers in one session ([APS](https://psychologicalscience.org/?p=193451)). Extra repetitions in the same session do not help: three versus nine problems in one session made no difference at one or four weeks ([Rohrer & Taylor, USF](https://digitalcommons.usf.edu/psy_facpub/1770/)). The design's "immediate reinforcement with fresh problems" after a partial miss should be one or two problems plus a redo the next day, not a drill run. FSRS agrees: with default FSRS-6 parameters, a same-day Good adds zero stability (computed with py-fsrs 6.3.2), so only the delayed redo moves the schedule ([py-fsrs scheduler](https://raw.githubusercontent.com/open-spaced-repetition/py-fsrs/main/fsrs/scheduler.py)). A skill that lapses long after its last review should get a worked example before the next attempt. Worked examples may be the more efficient tool for relearning after long delays ([Learning Scientists on Cao & Carvalho 2026](https://www.learningscientists.org/blog/2026/6/18-1)).

### Feedback must explain, and grading must not depend on the learner's judgment

Feedback roughly doubles the testing effect, g = 0.73 with feedback versus 0.39 without ([Rowland 2014](https://courseware.epfl.ch/assets/courseware/v1/fdde2f0aa590bf3b1324077a6bf1540c/asset-v1%3AEPFL%2BDEMO%2B2020%2Btype%40asset%2Bblock/Rowland2014-meta-analysis.pdf)). Information-rich feedback reached **d = 0.99**, against 0.46 for corrective-only ([Wisniewski et al. 2020](https://www.frontiersin.org/articles/10.3389/fpsyg.2019.03087/full)). Every attempt should end with a full worked solution that explains *why* each step works. In an engineering course, feedback delayed by a week produced better transfer than immediate feedback ([Mullet et al. 2014](https://profiles.wustl.edu/en/publications/delaying-feedback-promotes-transfer-of-knowledge-despite-student-/)). The scheduler already supplies that delay by bringing the skill back days later with a new problem, so immediate solutions remain correct. Errors made with high confidence are corrected unusually well, but confidence adds little beyond prior knowledge ([Sitzman et al. 2014](https://link.springer.com/article/10.3758/s13421-013-0344-3)). A one-tap confidence rating is useful for flagging high-confidence errors for a recheck within a day or two. It should not drive the memory model. Self-assessment drifts toward overconfidence, most of all among weak performers ([Learning Scientists on Hacker et al. 2000](https://learningscientists.org/blog/2017/2/16-1)). Grading against detailed idea-unit standards cut that bias from .14 to .06 ([Nederhand et al. 2018](https://repub.eur.nl/pub/109964/REPUB_109964-OA.pdf)). Auto-check every answer that can be checked, use step rubrics for the rest, and never ask a bare "did I get it?" One finding argues against letting the user retire skills at all: when students chose when to drop items, successive relearning gave **no exam benefit** ([RetrievalPractice.org](https://www.retrievalpractice.org/archive/2018/successive-relearning)).

### Target high success, vary the problem form, and hide the label

The popular "85% rule" is a result about gradient-descent learners on binary classification that was never tested on humans ([Wilson et al.](https://www.biorxiv.org/content/10.1101/255182v1)). The closest human evidence found that retention per minute of practice peaked when items were practiced at predicted recall of about **0.86–0.94**, with an inverted U ([Eglington & Pavlik 2020](https://pmc.ncbi.nlm.nih.gov/articles/PMC7567101/)). That supports a desired retention of 0.85–0.90 for reviews and higher success during acquisition. Accuracy during practice is a misleading signal. In one study, blocked practice scored 89% during practice versus 60% for mixed, then 20% versus 63% on the test ([Rohrer & Taylor 2007](https://www.Gwern.net/doc/psychology/spaced-repetition/2007-rohrer.pdf)). The dashboard's learning measure should be accuracy on delayed reviews, not practice accuracy. Seventy-two percent of learners judged blocking more effective, and only experience plus an explanation changed most minds ([Yan, Bjork & Bjork 2016](https://sites.lifesci.ucla.edu/psych-bjorklab/wp-content/uploads/sites/13/2016/11/YanBjorkBjork2016.pdf)). The app should say plainly that mixed practice feels harder.

Interleaving works partly because the learner has to recognize which problem type is in front of them. Show the skill name only after the attempt. Place confusable skills near each other, since items interleaved in immediate succession gave g = 0.73 versus 0.22 when spaced apart ([Brunmair & Richter 2019](https://www.psychologie.uni-wuerzburg.de/fileadmin/06020400/2019/Brunmair_Richter_in_press__2019_META-ANALYSIS_OF_INTERLEAVED_LEARNING.pdf)). Fact quizzes do not build higher-order skill ([Learning Scientists on Agarwal 2019](https://www.learningscientists.org/blog/2019/6/27-1)), and critics say Math Academy's number-swap practice entrenches shallow understanding ([Pershan](https://pershmail.substack.com/p/math-academy-wants-to-supercharge?open=false)). Problem generators must therefore vary form: representation, direction ("find a function whose derivative…"), wording, and which quantity is unknown. They also need "which method applies?" items and multi-skill synthesis problems as skills of their own. Formula and definition cards should require typing the answer, not recognizing it (cued recall g = 0.61 vs recognition 0.29 in [Rowland 2014](https://courseware.epfl.ch/assets/courseware/v1/fdde2f0aa590bf3b1324077a6bf1540c/asset-v1%3AEPFL%2BDEMO%2B2020%2Btype%40asset%2Bblock/Rowland2014-meta-analysis.pdf)). They should live inside the same queue: one adult learner's separate Anki deck for identities failed because it felt "disconnected" from his main practice ([Hecker update 5](https://frankhecker.com/2026/02/08/math-academy-update-5/)).

For exams, the optimal gap between study sessions in Cepeda's large study was about 23% of a 35-day retention interval and 8% of a 350-day one. Gaps that are too short cost far more than gaps that are too long ([Cepeda et al. 2008](https://www.evullab.org/pdf/CepedaVulRohrerWixtedPashler-PS-2008.pdf)). An exam-date constraint should pull each exam-tagged skill forward so its predicted retrievability on the exam date meets the target. A reasonable placement is 5–10 days before a test a month away (my inference from the ridgeline), keeping total daily load flat. Adherence is the main practical risk. When students controlled their own spacing at home, 35% completed versus 71% for massed practice ([Barzagar Nazari & Ebersbach 2018](https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2018.02170/pdf)). The app has to hold the schedule.

## FSRS can schedule skills only as a calibrated approximation

### The library, the model and its pitfalls

FSRS-6, with 21 parameters, is the current released model. The latest **py-fsrs is 6.3.2 (9 Aug 2026, MIT, Python ≥3.10)** ([PyPI fsrs](https://pypi.org/project/fsrs/)). FSRS-7 handles same-day reviews far better: benchmark log loss with same-day reviews included was 0.3206 versus 0.3842 for FSRS-6 ([srs-benchmark](https://github.com/open-spaced-repetition/srs-benchmark)). As of June 2026, though, it had not been released by the FSRS project or merged into Anki ([Anki forum](https://forums.ankiweb.net/t/when-will-anki-integrate-fsrs-7/69997)). Pin 6.3.2 behind an adapter interface so FSRS-7 can be swapped in later. Several behaviors of the library matter directly for this app.

| py-fsrs behavior | Consequence for this app | Fix |
|---|---|---|
| Retrievability uses whole days elapsed (`.days`) | R reads 1.0 for 24 hours after a review, which breaks same-day triage and reinforcement logic | Compute R yourself from fractional days with the same formula |
| UTC-only; naive datetimes raise ValueError | Time-zone bugs around the study-day rollover | Store UTC everywhere; compute the "study day" locally with a rollover hour |
| Same-day Good floors the stability increase at 1.0 | Same-day reinforcement never pushes a review later | Keep reinforcement short; schedule a next-day redo |
| Optimizer label: Again = 0, Hard/Good/Easy = 1 | "Hard" is learned as a successful recall | Use Hard only when the method was genuinely recalled |
| Optimizer returns defaults below 512 non-same-day reviews; needs `torch` | About 5 weeks on defaults at 15 reviews/day; a heavy dependency | Exclude the optimizer from the default build; log everything it needs from day one |
| Default learning steps are 1 and 10 minutes | Flashcard-style steps make little sense for multi-minute problems | Handle acquisition in app logic; set `learning_steps=()` |

Sources: [py-fsrs scheduler](https://raw.githubusercontent.com/open-spaced-repetition/py-fsrs/main/fsrs/scheduler.py), [py-fsrs optimizer](https://raw.githubusercontent.com/open-spaced-repetition/py-fsrs/main/fsrs/optimizer.py), [py-fsrs README](https://github.com/open-spaced-repetition/py-fsrs). The 5-week figure is arithmetic, not a source claim. Anki's default desired retention is 90%, and the manual warns that workload climbs quickly above 90% and becomes overwhelming above 97% ([Anki manual](https://docs.ankiweb.net/deck-options.html)). The FSRS-6 curve shows how strongly this setting drives the schedule: at a stability of 10 days, desired retention of 0.80, 0.85, 0.90 and 0.95 gives intervals of 33, 19, 10 and 4 days (computed from the py-fsrs interval formula). Start at 0.85–0.90 per course, let finished courses run lower, and once a few hundred reviews with real durations exist, compute a time-aware optimum. A failed problem costs many minutes, which argues for higher retention. A failure followed by a worked solution is also highly informative, which argues for lower. Only data can settle that trade-off.

### Why "recall" means something different for a skill

No study validates FSRS for skill-level scheduling with varied problems. An Anki forum volunteer put the practitioner skepticism directly in September 2026: for practice, "There's no evidence that either of the algorithms, or even spaced-repetition scheduling in general" applies, and a fresh problem helps more than repeating a card ([Anki forum](https://forums.ankiweb.net/t/questions-about-tuning-fsrs-for-math-logical-reasoning-problem-cards/70949)). Supporting evidence comes from elsewhere. Spacing works for math *problem types* ([Rohrer & Taylor, USF](https://digitalcommons.usf.edu/psy_facpub/1770/)). Skill-level forgetting models with per-skill decay (DAS3H) beat item-only models on three math tutoring datasets, for example AUC 0.826 versus 0.775 on Algebra 2005 ([DAS3H](https://ar5iv.labs.arxiv.org/html/1905.06873)). For a skill, R means "probability of solving a fresh, typical problem unaided," and differences in difficulty between problems add noise that flashcards don't have. Three practices contain that noise. Log predicted R against observed success, grouped into bins per course. Count a review as an FSRS event only when the problem sat in the skill's core difficulty band. Re-fit parameters per domain (math, physics/chemistry, C++) once each has 512 reviews, since Anki recommends separate presets for very different material ([Anki FSRS FAQ](https://docs.ankiweb.net/faqs/frequently-asked-questions-about-fsrs)).

### An automatic rating map, kept honest

No source gives a validated mapping from problem outcomes to the four FSRS buttons, so the map below is a synthesis. It follows Execute Program's rule that only giving up counts as forgetting ([Matuschak on Execute Program](https://notes.andymatuschak.org/zX7RdiHGbHYnkFznUr9VZx7)) and Anki's remark that FSRS "may even be more accurate if you only use Again and Good" ([Anki FSRS FAQ](https://docs.ankiweb.net/faqs/frequently-asked-questions-about-fsrs)). It also limits attempts, because WeBWorK students with unlimited attempts showed guessing 47.4% of the time versus 9.7% with a 7-attempt limit ([UBC CWSEI 2013](https://cwsei.ubc.ca/files/outcomes/EOY/Lo-Merchant-Piccolo_WebWork-Math_CWSEI-EOY2013.pdf)).

| Outcome | FSRS rating | Notes |
|---|---|---|
| Wrong after the attempt limit (e.g., 2), gave up, viewed the solution, or used a hint that revealed the method | Again | A genuine lapse, but only on a core-difficulty problem |
| Correct on the second attempt, after a minor nudge, with the "guessed" flag, or with low confidence | Hard | The optimizer treats this as a pass |
| Correct, unaided, first attempt | Good | The default success |
| Correct, unaided, fast, on a high tier | Easy | Rare; can be disabled entirely |
| Wrong because of a self-declared slip, with a corrected re-entry | Hard, capped per week | Log separately; never propagate to prerequisites |
| Wrong on a stretch problem (predicted P < ~0.5) | No FSRS event | Update the difficulty model only; offer the sub-skill diagnosis flow |

### Problem selection belongs to a separate difficulty model

FSRS decides *when* a skill is due. A lightweight Elo model should decide *which problem*. Elo with a decaying update size, U(n) = a/(1 + b·n) with a = 1 and b ≈ 0.05, matched full Rasch estimates at r ≈ 0.97 in a single online pass. About 10 answers suffice to estimate a learner's skill, but item difficulty needs about **100 learners** ([Pelánek, Elo in education](https://www.fi.muni.cz/~xpelanek/publications/CAE-elo.pdf)). A one-user app will never calibrate individual problems from its own data, so author-assigned tiers (OPL Level tags and exercise types are ready-made priors) carry difficulty, and pooled data could refine them only if copies ever share data. Studies target practice success between 65% and 75% ([Pelánek et al., UMUAI](https://www.fi.muni.cz/~xpelanek/publications/umuai-adaptive-practice.pdf); [EDM 2014](https://www.fi.muni.cz/~xpelanek/publications/EDM14-adaptive-facts.pdf)), and Math Academy tunes quizzes to about 80% ([Math Academy](https://mathacademy.com/how-our-ai-works)). The two research streams pull in different directions here. Learning science proposes harder tiers as stability grows. Scheduling wants a fixed "core" band so that pass or fail measures memory rather than difficulty. A workable reconciliation: define each skill's core band broadly, let it drift up modestly with stability, record the tier on every review, treat failures above the core band as non-lapses, and check calibration by tier.

### Partial credit through the prerequisite graph: build it, prove it, then switch it on

Math Academy's Fractional Implicit Repetition (FIRe) keeps a separate **encompassing graph** whose edges carry weights from 0 to 1: the fraction of a simpler skill practiced inside an advanced one. Credit flows down from passed advanced reviews, penalties flow up from failed simple ones, early credit is discounted, and "when speed < 1, implicit credit is discarded and explicit reviews are forced." A due review is never deferred to wait for an implicit knock-out ([Skycak, FIRe](https://www.justinmath.com/individualized-spaced-repetition-in-hierarchical-knowledge-structures/); [archived version](https://gwern.net/doc/www/www.justinmath.com/9af2ce40376e836660c237a0e971d1896a163eee.html)). Weights are set only for nontrivial, nearby pairs, with 0, 0.5 and 1 as the common values and products along chains for distant pairs. Skycak warns: "You don't want to give students credit for something they aren't actually practicing, or they'll forget it" ([Setting encompassing weights](https://justinmath.com/setting-encompassing-weights); [Hecker part 7](https://frankhecker.com/2025/02/14/math-academy-part-7/)). The propagation algorithm itself is proprietary, no study has evaluated it, and Matuschak found the hierarchical scheduling "too conservative": he forgot earlier material faster than it assumed ([Matuschak](https://notes.andymatuschak.org/Math_Academy)).

FSRS already discounts early reviews, since its stability gain scales with e^((1−R)·w10) − 1, so a clean way to layer fractional credit on top is the following proposal. On a passed explicit review of advanced skill A, for each encompassed skill B with effective weight w, compute B's Good-rated stability at its current fractional-day R. Move B's stability w of the way there. Do not reset B's last-review clock, and recompute B's due date. Credit that arrives early is automatically tiny. Skip implicit credit for skills in learning or relearning, recently failed, or with high difficulty (FIRe's speed < 1 analogue), and force an explicit review once implicit credit alone has doubled a skill's stability. Penalties flowing up should be damped (shrink an encompassing skill's stability by w × ~0.3, or simply pull its review earlier) and explained to the user. That avoids ALEKS's "lost 55 topics" experience ([Common Sense review](https://www.commonsense.org/education/reviews/aleks/teacher-reviews/5118207)). Keep implicit events in their own table and out of the optimizer's training logs. Excluding them biases fitted stability growth upward, and including them biases it the other way. Neither is clean.

The design calls for partial credit, and it should ship. I recommend a sequence for it: run credit in **shadow mode** for the first several weeks. In shadow mode the app computes and stores a credited stability alongside the plain one but schedules from the plain state. Every explicit review of a sub-skill then tests both predictions, and the credit can be turned on once the credited predictions prove at least as well calibrated. Routing errors back to foundational skills is lower-risk and goes live immediately. The design already has the user tag the broken sub-skill and confirms the tag with a quick direct check. That is a sound low-data method; psychometric diagnosis models such as DINA and PFA need far more data than one learner produces ([Stan DINA case study](https://mc-stan.org/learn-stan/case-studies/dina_independent.html); [Pelánek et al., AFM analysis](https://www.fi.muni.cz/~xpelanek/publications/afm-analysis.pdf)). If the check passes, the miss was a slip or a failure to integrate steps, and the advanced skill takes the hit. If the check fails, the sub-skill gets Again and the advanced skill is penalized less. No study quantifies how accurately learners self-diagnose ([arXiv 1602.07253](https://arxiv.org/pdf/1602.07253)), so log how often each tag is confirmed by the check. Offer a fixed error taxonomy that includes "didn't know where to start." That error belongs to the advanced skill and is exactly what interleaving trains.

### Graph, mastery and placement

Use one set of skill nodes with two edge types: a prerequisite DAG (validated by topological sort, stored as its transitive reduction) for unlocking and diagnosis, and weighted encompassing edges for credit. Math Academy runs about **300 topics per course** ([Math Academy](https://mathacademy.com/how-our-ai-works)). At that granularity, College Algebra, Trig and Calc 1 would come to roughly 600–900 skills, or 100–250 at section level (researcher's estimate). An LLM can draft skill lists and candidate edges with suggested weights from {0, 0.25, 0.5, 1}. A human should review them in confidence order and skip edges implied by transitivity. In the ACE study, expert-in-the-loop ranking kept about 90% path recall at half the expert effort, and GPT-4o-mini alone reached F1 71.92 ([ACE, JEDM](https://distantreader.org/stacks/journals-ojs/jedm/jedm-737.htm)). Disabling a course section should hide its skills from the queue without removing them from the credit graph. Whether disabled skills still receive credit is an open setting.

For mastery, the simplest criteria hold up: the choice of threshold and data sources matters more than the model, and an exponential moving average is adequate ([Řihák & Pelánek](https://www.ics.muni.cz/en/research/publications/1448676)). Copy ALEKS's distinction between *Learned* and *Mastered* ([McGraw Hill](https://www.mheducation.com/prek-12/support/knowledge/aleks-why-must-i-review-a-topic-i-have-already-mastered.html)). A skill is learned when acquisition hits two or three in a row. It is mastered only after about three successful spaced reviews and a stability above a chosen threshold, such as 21–30 days or the time to the next exam (a design choice). On graduation, start the FSRS card by replaying the real acquisition attempts rather than inventing a stability. For placement, Math Academy and ALEKS both use the graph so that a pass on an advanced item implies its prerequisites. ALEKS caps its initial check at about 20–30 questions with an "I Don't Know" button ([McGraw Hill](https://www.mheducation.com/support/aleks-support-center/knowledge/what-is-a-knowledge-check.html)), and Math Academy uses 20–60 ([Hecker part 7](https://frankhecker.com/2025/02/14/math-academy-part-7/)). Placed-out skills can be created directly as Review-state py-fsrs cards with conservative, provisional stability. Use about 2.3 days for skills inferred only from descendants and about 10 days for skills passed directly (researcher's proposal), and let the first real review on a fresh problem confirm or demote them.

## Zero wrong keys means making answers computations

### Checking the student's answer is its own reliability problem

Mature systems separate value equivalence from form. WeBWorK compares formulas at five random test points inside a declared domain with a relative tolerance of 0.001, and it advises keeping logs and roots on positive inputs "because floating-point arithmetic is unreliable for negative inputs" ([WeBWorK context flags](https://webwork.maa.org/wiki/Context_flags); [FormulaTestPoints](https://webwork.maa.org/wiki/FormulaTestPoints)). STACK runs symbolic `simplify(a−b)=0` plus about 40 specialized answer tests chained in response trees, with form tests such as FacForm and LowestTerms kept separate from equivalence ([STACK answer tests](https://docs.stack-assessment.org/en/Authoring/Answer_Tests/)). The bank schema needs typed answers, each with its own comparator. The types are: exact or decimal number; expression with variables and a domain; equation; solution set (interval, union or finite set, including the empty set); unordered list; ordered tuple or point; matrix; a special union of number, ∞, −∞ and DNE for limits; quantity with units; multiple choice; and self-graded proof.

SymPy alone is not a reliable equivalence oracle. Local tests in SymPy 1.14.0 found these failures:

- `simplify` misses `2ln|x|` = `ln(x²)` and a Cardano expression that equals 2.
- `.equals()` returns None on `asin(sin x)` versus `x`.
- A student's `x` parsed with default assumptions and a key built with a real `x` are different symbols.
- `"sinx"` splits into four symbols.
- `"e^x"` treats `e` as a variable.
- `(-8)^(1/3)` evaluates to a complex root ([SymPy parsing docs](https://docs.sympy.org/latest/modules/parsing.html); local runs reported in the research notes).

The most serious problem is that **`parse_expr` calls `eval`**. A critical 2026 CVE (CVSS 9.8) exploited exactly that ([NVD CVE-2026-55546](https://nvd.nist.gov/vuln/detail/CVE-2026-55546)). In local testing, restricting `global_dict` still let the input `x.__class__.__mro__[-1].__subclasses__()` run. The recommended checker works in layers:

1. Parse through a whitelist. MathLive's MathJSON tree, translated by hand into SymPy, avoids `eval` entirely.
2. Inject the problem's own symbol objects with their assumptions.
3. Run cheap exact checks.
4. Evaluate numerically at 10–20 high-precision points per variable inside the declared domain, with at least one point per connected piece. Fail the answer if it is undefined where the key is defined. This layer decides most cases.
5. Run an optional symbolic confirmation in a subprocess killed after 1–2 seconds.
6. Return one of three verdicts: correct, incorrect, or undecidable.

In the student UI, "undecidable" falls back to a self-grade. In the bank pipeline it never counts as correct. Equations use STACK's numerator-ratio test. Sets and intervals compare exactly as canonical SymPy objects. Antiderivatives are checked by differentiating numerically. Units are converted to SI and compared with a tolerance based on significant figures ([SymPy units](https://docs.sympy.org/latest/modules/physics/units/index.html)).

False negatives from the grader are a second source of error, and they corrupt FSRS data just as badly as wrong keys. Rule-based verifiers reach at least 99% precision but average only **~86% recall**, so they reject about one correct answer in seven, mostly over format, equivalent representations and units ([arXiv 2505.22203](https://arxiv.org/html/2505.22203v2)). One verifier mislabeled 38.5% of correct responses ([TinyV](https://arxiv.org/html/2505.14625v2)). Copy STACK: "Separating validity from assessment is a key design feature" ([STACK philosophy](https://docs.stack-assessment.org/en/About/The_philosophy_of_STACK/)). Show "We read your answer as: …" with explicit multiplication before grading, treat syntax errors as "try again," and offer a "dispute this grading" button that logs the case and does not count the attempt. Store a known-wrong answer with every problem so the CI suite proves the checker rejects it. Proofs and "show that" items should be self-graded against a model solution and a checklist of 3–6 key steps. In a proof-grading benchmark, an LLM grader without a reference solution and marking scheme inflated scores by 0.92 points on a 7-point scale and over-scored polished but wrong proofs ([ProofBench](https://arxiv.org/html/2510.13888v1)). An offline app couldn't call an LLM grader at runtime anyway.

### Most residual errors will be broken problems, not wrong arithmetic

Frontier models now solve standard competition problems at 95–99% ([BenchLM AIME 2026](https://benchlm.ai/md/benchmarks/aime2026.md)), so the remaining errors in a bank come from bad problems and bad keys. Manually cleaning well-used benchmarks found far more ambiguous or ill-posed items than mislabeled ones. GSM8K had **8.7% removed versus 0.3% mislabeled**, and SVAMP 9.0% versus 1.0%. These are lower bounds, because flawed items that every model answered "correctly" go unnoticed ([Platinum benchmarks](https://arxiv.org/pdf/2502.03461)). Model-generated answers to synthetic problems were wrong **30.5%** of the time, mostly through logic errors ([MathClean](https://arxiv.org/html/2502.19058v1)). Models are weak at finding these flaws. Without a hint, the best model flagged only 33.3% of faulty problems. Told a problem *may* be faulty, models caught 79–96%. Told it was valid, they fell back to the no-hint rate ([arXiv 2410.18921](https://arxiv.org/pdf/2410.18921)). Agreement between solvers is a coarse signal. GPT-4.1 answers with self-consistency of 0.8 or higher were still wrong 48% of the time on a hard multiple-choice set, and models from different providers chose the *same* wrong option more often than chance. Confident errors on numeric AIME answers were more dispersed, so agreement means more on free-response numeric answers ([arXiv 2607.08065](https://arxiv.org/pdf/2607.08065)). Keep answers free-response and convert multiple-choice sources wherever possible.

The strongest guarantee is to make the key a computation. Code computes the answer from structured parameters, and the model writes only the prose around it. This is the model behind WeBWorK and GSM-Symbolic, which verified templates with automated checks, 10 manual samples per template, and a requirement that at least two models answer each instance correctly ([GSM-Symbolic](https://arxiv.org/html/2410.05229v2)). Code-based self-verification also helps: having GPT-4 write code to check its own answer raised zero-shot MATH accuracy from 53.9% to 84.3% ([arXiv 2308.07921](https://arxiv.org/abs/2308.07921)). The acceptance rule should depend on where a problem came from. The table below synthesizes the research. No source has measured the joint false-acceptance rate of such a pipeline.

| Provenance | Signals required to accept |
|---|---|
| Template (parameters with constraints; answer computed in code) | Verify the template once with a sweep over 1,000–10,000 seeds checked by an independent SymPy route, back-substitution and degenerate-case checks, plus 5–10 blind LLM solves including extreme parameters. Freeze it by content hash. No per-instance LLM calls |
| Source with official key (OPL computed answer, OpenStax odd solutions, Kyoto official answers) | Key matches a blind model solve under the SymPy checker, and the item passes the well-posedness audit |
| Source without key (OpenStax evens, UTokyo math, OpenIntro evens) | Blind natural-language solve matches an independent code or SymPy solve (different prompt, ideally a different model), back-substitution passes where possible, and the item passes the well-posedness audit |
| AI-original with a CAS-checkable answer (incl. Gaokao/CSAT-style originals) | Generator's intended answer, blind solve and code solve all agree; adversarial well-posedness audit; uniqueness check that the full answer set was found |
| AI-original, proof or olympiad style | Never auto-graded; ship as self-graded with a rubric, quarantined until the owner has solved it |

Several checks cost no tokens at all. Substitute every claimed root and confirm the full solution set with `solveset` over the stated domain, which catches missing and extraneous roots. Differentiate claimed antiderivatives, compare limits against high-precision evaluation near the point, verify linear algebra exactly, and run dimensional analysis on physics answers. The well-posedness audit should run *before* solving, prompted as "this problem may be flawed; list missing conditions, contradictions, ambiguity, multiple answers," because that hinted framing is what lifted detection to 79–96%. Never let an LLM judge overrule a SymPy "not equal." Use it only to rescue format mismatches, and then only by producing a canonical expression that SymPy confirms. The user's rule of dropping disputed problems matches the evidence. After release, a "report problem" button should hide the item at once, exclude the attempt from scheduling, and queue the problem for re-verification with a stronger model and a different method. Content packs must never contain executable code, an Anki lesson ([Anki manual: Math](https://docs.ankiweb.net/math.html)). The cleanest way to reconcile templates with that rule is to pre-generate and verify many instances per template at build time (50–200, for example) and ship them as frozen data. With pools that large, a skill effectively never repeats a problem.

### Translation, deduplication and difficulty priors

For Japanese, math experts disagreed with GPT-4o's draft translations on *content* in 12.8–15.2% of PolyMath problems, and the authors noted that "a single mistake in a key term can distort the entire problem" ([PolyMath](https://arxiv.org/pdf/2504.18428)). Verify translations the way extraction is verified. Keep a glossary of terms that change meaning: 以上/以下 are inclusive and より大きい/未満 strict, 自然数 starts at 1, and 示せ/証明せよ marks a proof item. Check in code that every number and formula survives translation unchanged. Then blind-solve the English version and accept it only if it reproduces the official Japanese answer. A translation error that changes the meaning almost always changes the answer. For deduplication, apply exact hashing, then MinHash-LSH, then embedding similarity, as Big-Math did ([Big-Math](https://arxiv.org/pdf/2502.17387)). But use a high threshold, around 0.9 cosine, for automatic removal, because related problems from the same skill are wanted here. Store a "structure hash" with the numbers replaced so template siblings are recognized rather than deleted. For difficulty before any user data exists, direct LLM ratings are poor. In simulated-student studies a *weaker* model predicted difficulty better than stronger ones ([arXiv 2601.09953](https://arxiv.org/abs/2601.09953v1)). Use the failure rate of a small model over several attempts, plus source level and step count, as a prior.

### Token cost is cents per problem when deterministic code does most of the work

Extraction, LaTeX validation, parsing, equivalence, back-substitution, deduplication and template sweeps cost zero tokens. Current prices per million tokens are **Haiku 5.5 $0.10 in / $0.50 out, Sonnet 5.5 $2 / $10, and Opus 5.5 $4 / $20**. The Batch API halves both input and output prices. Cache reads cost 0.1× base input (0.05× on Opus 5.5 and Sonnet 5.5), and the pricing page confirms that **batch and caching discounts stack** ([Claude API pricing](https://platform.claude.com/docs/en/about-claude/pricing), checked 2026-11-01). The researcher's estimates follow from these prices. Tagging with Haiku in batches against a cached skill taxonomy costs about $0.00003 per problem. A verified routine algebra, trig or Calc 1 problem (two independent Sonnet solves plus an audit) costs about **$0.02–0.03**, or $200–300 per 10,000 problems. Hard or AI-original problems cost $0.25–0.35 per *accepted* problem, more once rejections are counted. Templates cost $0.05–0.20 once each and nothing per instance. Use an escalation ladder: a cheap solve first, a stronger model only on disagreement, early stopping on agreement (which cut samples 60% at equal error in [arXiv 2607.08065](https://arxiv.org/pdf/2607.08065)), and a drop if the dispute persists. How reasoning tokens are billed was not confirmed, so treat these estimates as order-of-magnitude.

### License mixing and the publish switch

CC conditions apply only when material is "Shared," which means provided "to the public" ([CC BY-NC-SA 4.0 legal code](https://creativecommons.org/licenses/by-nc-sa/4.0/legalcode.en)). A strictly private build triggers almost nothing. "Anyone could download their own copy" is the publish switch. Once it is on, every item needs attribution with modifications marked, adapted items carry ShareAlike, the app cannot be sold because of NC, GFDL items need their license text, and Qt's LGPL requires the license text, a source offer and re-linkability ([Qt LGPL obligations](https://www.qt.io/licensing/open-source-lgpl-obligations)). Keeping differently licensed items as separate, attributed records is a collection, not an adaptation. Rewording, translating or turning a static problem into a template *is* an adaptation ([CC FAQ](https://creativecommons.org/faq/)). An adaptation can never combine BY-SA text (OpenIntro, Active Calculus, Light and Matter, the UBC Contrib files) with BY-NC-SA text (OpenStax, CLP, OPL), because no license satisfies both ShareAlike clauses ([CC compatible licenses](https://creativecommons.org/share-your-work/licensing-considerations/compatible-licenses/)). Store these fields per item from day one: source id, title, creators, SPDX license and URL, original path plus commit, a modified flag with a description, a third-party flag, and a translation/unofficial-solution label. An About/Credits screen generated from that metadata satisfies attribution "in any reasonable manner."

### Physics, chemistry and C++ need their own grading conventions

OpenStax physics and chemistry solutions are free text with units and implied significant figures, such as "v_avg = 4.0 i + 2.0 k m/s," with no separate numeric field. They must be parsed into value-unit pairs (with pint or SymPy units) and graded with a tolerance derived from the given significant figures. Conceptual and multi-part items become self-graded. WeBWorK's PG language has unit, significant-figure and chemical-reaction answer contexts, but little calculus-level physics and no chemistry bank ([OPL repo](https://github.com/openwebwork/webwork-open-problem-library); [PG](https://github.com/openwebwork/pg)). Chemistry will need authored stoichiometry and equilibrium templates. Items the user writes himself carry no third-party license. For C++, treat the scheduled unit as a *pattern* and serve a different problem from it when possible. A coding practitioner warns that short-interval successes mislead and that understanding is reliable only at 15–30 day intervals ([LeetCode Tip 12](https://www.redgreencode.com/leetcode-tip-12-how-to-use-spaced-repetition-part-2/)).

## PySide6 with one bundled web view is the right stack

### Architecture borrowed from Anki, minus what Anki needs for scale

Anki keeps almost all its logic in a GUI-free library (a Rust core behind the Python `anki` package), with a PyQt GUI and Svelte pages loaded into QtWebEngine and bridged by QWebChannel. It serves user content under a no-script content security policy whose source code warns "Never add allow-scripts" ([Anki architecture](https://github.com/ankitects/anki/blob/main/docs/architecture.md); [mediasrv.py](https://github.com/ankitects/anki/blob/main/qt/aqt/mediasrv.py)). The parts to copy are a `core/` package with no Qt imports (scheduler adapter, database, grading, content loading, testable with plain pytest), one SQLite user file per profile, automatic rolling backups, and the rule that content never carries code. The parts to skip are Rust, protobuf, add-ons and sync. Tauri or Electron would still need a PyInstaller-built Python sidecar for SymPy, per target triple, plus a second language ([Tauri sidecars](https://v2.tauri.app/develop/sidecar/)). Python with PySide6 keeps grading and scheduling in-process.

### Bindings, rendering and input

Use **PySide6 6.12** (released 8 Oct 2026; LGPL-3.0, Python 3.10 to 3.15, and macOS 14+ for the universal2 wheels) rather than PyQt6, which is GPL v3 or commercial ([PyPI PySide6](https://pypi.org/project/PySide6/); [PyPI PyQt6](https://pypi.org/project/PyQt6/)). One trap: in 6.12, QtWebEngine moved out of PySide6-Addons into a separate `PySide6_WebEngine` package. It must be installed explicitly (`pyside6[webengine]`), and its wheel is **249.8 MB on macOS and 131.7 MB on Windows** ([PyPI PySide6-WebEngine](https://pypi.org/project/PySide6-WebEngine/); [PySide6-Addons](https://pypi.org/project/PySide6-Addons/)). Host the review surface in one long-lived QWebEngineView. Render with **KaTeX 0.19.1**, self-hosted with its `fonts/` folder ([KaTeX](https://katex.org/docs/browser)), and keep MathJax 4 as a fallback for long derivations, since it added line breaking ([MathJax 4](https://www.mathjax.org/MathJax-v4.0.0-available/)). KaTeX only displays math, so input needs **MathLive** (MIT, self-hostable, about 800 LaTeX commands, a virtual keyboard, and export to LaTeX, MathJSON and ASCIIMath) ([MathLive](https://github.com/arnog/mathlive); [integration guide](https://mathlive.io/mathfield/guides/integration/)). Send MathJSON to Python over QWebChannel, which is asynchronous and JSON-only ([Qt WebChannel](https://doc.qt.io/qt-6/qtwebchannel-javascript.html)). If a LaTeX route is used, `latex2sympy2_extended` 1.11.0 adds matrices and sets but needs an exactly pinned ANTLR runtime ([PyPI](https://pypi.org/project/latex2sympy2-extended/)). SymPy's own `parse_latex` "may fail to fully parse an expression, yet not throw a warning" ([SymPy parsing](https://docs.sympy.org/latest/modules/parsing.html)). Serve bundled assets through a custom URL scheme or Qt resources rather than `file://`, and block all non-local requests. The exact Qt APIs for both (`QWebEngineUrlSchemeHandler`, a request interceptor) come from general knowledge and should be confirmed. Use Python 3.12 or 3.13: Nuitka 4.0 does not yet support 3.14 ([Nuitka 4.0](https://nuitka.net/posts/nuitka-release-40.html)), and Anki ships 3.13 ([Anki releases](https://github.com/ankitects/anki/releases)).

### Data design that survives content updates

Ship problems in a read-only `content.db` (journal_mode=DELETE, opened with `mode=ro`). Keep user data in a separate `user.db` in WAL mode under `platformdirs.user_data_dir` ([platformdirs](https://pypi.org/project/platformdirs/)). The two connect through `ATTACH`, with writes going only to `user.db`, because transactions across attached WAL databases "are not atomic across all databases as a set," and WAL "does not work over a network filesystem" ([SQLite WAL](https://www.sqlite.org/wal.html)). Reference problems by permanent string IDs. A typo fix bumps a revision number, a changed answer is flagged so the user can reset that card, and a removed problem is marked retired, never deleted, so its history stays valid. The review log should be append-only and record:

- UTC time and duration in milliseconds;
- the raw and parsed answer;
- the verdict, attempts, hints, flags, confidence and error type;
- the problem id, tier and revision;
- whether the event was explicit or implicit;
- the scheduler-parameters id and app version.

That makes re-fitting and shadow-mode evaluation possible later. Version the schema with `PRAGMA user_version` and forward-only migrations, taking a backup before each migration. Back up the user database every 30 minutes and on close, with daily, weekly and monthly retention, the way Anki does ([Anki backups](https://docs.ankiweb.net/backups.html)). Warn when the data folder sits inside Dropbox, OneDrive or iCloud ([Anki files](https://docs.ankiweb.net/files.html)). Leave `fsrs[optimizer]` out of the default build because it pulls in PyTorch ([py-fsrs optimizer](https://github.com/open-spaced-repetition/py-fsrs/blob/main/fsrs/optimizer.py)). Ship it as an optional add-on, or export review logs as CSV to optimize elsewhere.

### Packaging depends on an operating system that is still unknown

Use **PyInstaller 6.22.3 in onedir mode**. It "is not a cross-compiler," so each OS builds its own package ([PyPI pyinstaller](https://pypi.org/project/pyinstaller/)). Its macOS framework handling fixed QtWebEngine code-signing problems ([PR #7619](https://github.com/pyinstaller/pyinstaller/pull/7619)). Avoid onefile mode, which unpacks to a temporary folder on every launch. QtWebEngine needs its helper process and resource files deployed, and on macOS the helper must be signed with its entitlements ([Qt WebEngine deploying](https://doc-snapshots.qt.io/qtwebengine/qtwebengine-deploying.html)).

**On a Mac**, Apple Silicon requires every executable to be signed, even if only ad hoc. An ad-hoc-signed app that was built locally and never quarantined launched normally in testing on macOS 26 ([Eclectic Light](https://eclecticlight.co/2026/08/11/how-can-you-run-code-that-hasnt-been-notarised/comment-page-1/)), so building on the developer's own Mac avoids Gatekeeper entirely. Downloaded copies hit the warning, Sequoia removed the Control-click bypass in favor of System Settings → Privacy & Security → Open Anyway ([Macworld](https://www.macworld.com/article/2457844/what-to-do-when-you-cant-open-an-app-you-just-installed-in-macos-sequoia.html)), and only the $99/year Developer ID plus notarization removes it ([flaviocopes](https://flaviocopes.com/apple-developer-free-vs-paid/)). **On Windows**, unsigned builds get a "strong SmartScreen block." EV certificates no longer bypass SmartScreen (that ended in 2024), and Artifact Signing (about $9.99/month, individuals in the US and Canada) builds reputation only over time. A free Microsoft Store account, with Microsoft re-signing the MSIX, is the only no-cost way to avoid the warning ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)). CI on GitHub Actions should build on `windows-latest` and `macos-latest` (arm64). The Intel macOS runner disappears in fall 2027 ([GitHub changelog](https://github.blog/changelog/2025-09-19-github-actions-macos-13-runner-image-is-closing-down/)). Each build should end with a `--self-test` run of the frozen app (open the database, render one problem offscreen, grade one answer) to catch missing fonts, parser modules and WebEngine resources.

### Keeping an agent-written codebase coherent

Most of this code will be written by an AI agent, so layering and conventions have to be enforced mechanically. Use an import-linter contract ("core must not import PySide6"), ruff and mypy on `core/`, typed boundary models shared by Python and JavaScript, an AGENTS.md or CLAUDE.md with the rules, and architecture decision records (ADRs) for each big choice, so a later session doesn't "helpfully" switch to PyQt or a CDN. Pin every dependency, vendor KaTeX and MathLive with their license files, and generate a THIRD_PARTY_LICENSES file at build time. Problems should be authored as one YAML or Markdown file each in Git and compiled into `content.db` by a build script. That script should fail CI if any LaTeX fails KaTeX strict rendering, any answer spec fails to parse, a canonical answer fails its own checker, or a stored wrong answer passes. Add a test that fails if any code path attempts an outbound connection. For the later C++ phase: on Windows, ship w64devkit, a portable, fully offline MinGW-w64 GCC toolchain, as an optional download ([w64devkit](https://github.com/skeeto/w64devkit)). On macOS, rely on Apple's Command Line Tools rather than redistributing them ([Apple](https://developer.apple.com/documentation/xcode/installing-the-command-line-tools.md)). Run compiled code with time and memory limits, and use CodeMirror 6 in the same web view, because QScintilla is GPL and tied to PyQt ([PyPI QScintilla](https://pypi.org/project/QScintilla/)).

## Existing products show what makes learners quit or stop trusting

Math Academy is the closest analogue, and its mechanics are worth copying. Lessons open with a worked example and use "two correct in a row" to advance. A lesson that fails twice halts and returns "within a few days," with prerequisites prioritized for review. Missed quiz topics go to immediate review. The reported first-attempt pass rate is 93% ([Math Academy FAQ](https://www.mathacademy.com/faq); [How Our AI Works](https://mathacademy.com/how-our-ai-works)). Its users' complaints map directly onto this design. A retired adult tracked several courses at about 30–42 points a day with many days off, and his late-course lesson-to-review ratios ran 1:2 to 1:2.7, which Discord users call "review hell" ([Hecker update 5](https://frankhecker.com/2026/02/08/math-academy-update-5/)). He called the diagnostic "a brutal and dispiriting experience" with no obvious exit and found the pace estimates untrustworthy ([Hecker part 10](https://frankhecker.com/2025/02/17/math-academy-part-10/)). Matuschak described the algorithmic queue as creating "a feeling of passivity," predicted that topic-labeled reviews "significantly harm transfer," and said templated proofs meant he "never has to choose a proof strategy" ([Matuschak](https://notes.andymatuschak.org/Math_Academy)). Pershan passed via "accumulated ability to answer multiple-choice questions I didn't understand" ([Pershan](https://pershmail.substack.com/p/math-academy-wants-to-supercharge?open=false)). A reader published by FSRS's author asked for an "I don't know this topic" option, which Math Academy declined for fear of misuse ([First month report](https://lmsherlock.substack.com/p/my-first-month-with-math-academy)). That fear does not apply to a single-user tool.

ALEKS contributes the "ready to learn" frontier and an "I Don't Know" button. It also shows the cost of punitive checks that block progress and, after one wrong answer, can send a student back across dozens of topics ([Huntley Voice](https://huntleyvoice.com/21455/thevoice/math-program-aleks-is-frustrating-and-stressful/)). A meta-analysis found ALEKS "as good, but not better than" traditional teaching ([Fang et al. 2019](https://digitalcommons.memphis.edu/facpubs/7254)), a reminder that adaptivity does not replace content quality. Khan Academy users complain that course mastery "never seems to go down" and reflects cramming ([Khan community](https://support.khanacademy.org/hc/vi/community/posts/17266266115469/comments/17689505634829)). Displayed mastery should come from today's FSRS retrievability, shown gently as "fading." Streaks can come to matter more than learning, and users who break one are more likely to quit ([Decision Lab on Silverman et al.](https://thedecisionlab.com/insights/consumer-insights/streak-creep-the-perils-of-too-much-gamification)). Duolingo's forced linear path drew a "worst update ever" backlash, partly because one user "can no longer pick easier lessons when tired" ([NBC News](https://www.nbcnews.com/tech/tech-news/duolingos-update-redesign-luis-von-ahn-interview-rcna44655)). That argues for an "easier set today" option alongside the recommended queue.

Anki's lessons concern workload and settings. Users drift into a "death spiral" of backlogs, find the settings jargon-heavy, and miss a vacation mode ([LessWrong guide](https://www.lesswrong.com/posts/7Q7DPSk4iGFJd8DRk/an-opinionated-guide-to-using-anki-correctly); [Capterra](https://www.capterra.com/p/229584/Anki/reviews/)). FSRS-era Anki answered with a load balancer that picks lighter days within the fuzz range, Easy Days, and the helper add-on's Postpone, Advance and Schedule-a-Break actions ([Anki load balancer](https://raw.githubusercontent.com/ankitects/anki/main/rslib/src/scheduler/states/load_balancer.rs); [FSRS Helper](https://github.com/open-spaced-repetition/fsrs4anki-helper)). Anki suspends leeches at 8 lapses ([Anki leeches](https://docs.ankiweb.net/leeches.html)). Here a leech should instead trigger a fix: prerequisite repair or a worked example. Self-grading is lenient in practice: in Quantum Country's data, half of long-term lapses came from 12% of questions ([Matuschak](https://notes.andymatuschak.org/z3W7SG6BkSYyZD4cCqN6znd)). Mistake notebooks (错题本) work only when each error is analyzed for where it went wrong, why, how to fix it, a similar problem and a one-line reminder, starting with five mistakes rather than fifty ([163.com](https://www.163.com/dy/article/L45VFT0V0556FBHS.html)). Taken together, these lessons say every queue item should carry a reason tag (due review, prerequisite repair, new skill, leech fix). The app should never show a raw overdue count, should show "Today: N questions" with a 7–30 day forecast and calibrated retention per course, and should acknowledge section and course milestones, which Hecker found missing ("as exciting as watching your car's odometer roll over").

## A first milestone built around Stewart 4.1–4.7

The first target, Stewart's Chapter 4 sections 4.1–4.7, is applications of differentiation: extreme values, the Mean Value Theorem, how derivatives shape a graph, indeterminate forms and l'Hospital's Rule, curve sketching, and optimization (confirm section titles against his edition). It is a demanding first slice for the answer checker. It needs finite sets (critical numbers, values of c), intervals and unions (where a function is increasing or concave up), the limit union of number, ±∞ and DNE, ordered pairs (local extrema), quantities with units (optimization word problems), structured curve-sketching features entered as typed values rather than drawings, and self-graded "show that" items for the Mean Value Theorem. Its errors also route backward into derivative rules, solving equations, factoring, sign analysis and trig, so the milestone must include a thin slice of those prerequisite skills even though College Algebra and Trig come first in the overall rollout. Content should come from CLP-1, OpenStax Calculus Volume 1, APEX and Active Calculus, with Stewart-tagged OPL files excluded and BY-SA and BY-NC-SA text never merged. Drill skills should be backed by templates. The order below front-loads the parts that every later course reuses.

## Conclusion

The research turns the project from "build an Anki for problems" into building two systems, each held to its own standard of evidence. One is a scheduler whose model is admittedly approximate. Its job is to log every review well enough to test that approximation: calibration bins, shadow-mode credit, recorded triage policies, durations. The other is a content pipeline whose output must be trusted absolutely. Its job is to move every possible answer key from something a model wrote to something code computed, and to treat ill-posed problems, not arithmetic slips, as the main enemy. Most of the hard, unvalidated questions (whether FSRS fits skills, how much implicit credit is safe, which backlog order works for a prerequisite graph, what retention target suits multi-minute problems) cannot be answered from the literature, but they can be answered within a few months by a single disciplined user whose app records the right fields from the first day.

The other implication is about sequencing. The design's ambitious features, such as partial credit, compression of due reviews, and exam-style synthesis problems, add value only on top of three plain foundations: an acquisition phase that makes first retrievals succeed, a grader that rarely says "wrong" to a right answer, and a queue that never presents an unbounded pile. Math Academy's critics and Anki's abandoned decks fail at those foundations, not at the clever parts. A first milestone that gets them right for Stewart 4.1–4.7 will be reused by every course that follows.
