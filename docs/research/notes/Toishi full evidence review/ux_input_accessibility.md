## 1. Math answer input: what does the evidence say about the MathLive field, plain-text mode, shape helpers, the "We read your answer as ..." preview, and syntax errors that do not count as attempts?

### Takeaway
Previewing the parsed answer before judging it, and treating unparseable input as "invalid" rather than "wrong", is the best-documented practice in computer-aided maths assessment (STACK, WeBWorK, Isaac Physics) and addresses a real, measured error class (operator precedence and implicit multiplication). The support is practitioner experience plus observational platform data, not controlled trials; I found no study of MathLive usability, no data on keyboard-only maths entry on a Mac, and survey evidence that entry friction makes students avoid symbolic questions, so the input box is the highest-risk UI element.

### Cited Findings

#### Current design (spec IDs and built code)
- [Local file] The student types in a MathLive field (typing `/` makes a fraction, `^` a superscript, `sqrt` a root; optional on-screen math keyboard) or in plain-text mode; a live preview reads "We read your answer as ..." with multiplication made explicit; a syntax error or wrong answer shape shows inline and never counts as an attempt; Enter submits, Shift+Enter submits "unsure"; a wrong first attempt shows "Not quite" and nothing else; two attempts by default — [spec.md, "Answering" steps 1-4 and MATH-4 to MATH-7](/docs/spec.md)
- [Local file] MATH-6: `sinx` gets "Did you mean sin(x)?" and `e^2x` displays as e squared times x; MATH-7: for intervals, sets and points the field offers union, infinity, DNE, none and bracket buttons — [spec.md](/docs/spec.md)
- [Local file] ADR-0005: the ascii-math round trip was lossy (`DNE` became `D N E`), so the LaTeX path was chosen, and text answers use plain text because the math field drops spaces (spec MATH-4 still says the field outputs MathJSON, so spec and decision have drifted) — [0005-math-input-path.md](/docs/decisions/0005-math-input-path.md)
- [Local file] Built behaviour: the math field is created with `math-virtual-keyboard-policy="manual"`; the shape helpers are one roving-tabindex toolbar (arrow keys move between them); the preview sits in an `aria-live="polite"` region — [MathAnswer.svelte](/web/src/components/MathAnswer.svelte)
- [Local file] Built behaviour: letters, digits and Space never fire shortcuts while focus is in a text field; Enter, Shift+Enter, Esc (pause) and backtick (switch math/plain) do, "because the answer box has focus nearly all the time" — [shortcuts.ts](/web/src/lib/shortcuts.ts)
- [Local file] Hand test on macOS 26.6.2: typing, Cmd+Z and Shift+Cmd+Z work in the math field; NOT yet checked: paste, dead keys (Option+E e), alert sound while typing; clicking Hint takes focus out of the answer box — [backlog.md](/docs/backlog.md)

#### Evidence: input errors and validation before judging
- [Practitioner/expert opinion; vendor docs] STACK (the main open-source maths assessment engine) states its design rule: "The basic idea is to reject things as "invalid" to stop students being penalized on a technicality." — [STACK docs, Inputs](https://docs.stack-assessment.org/en/Authoring/Inputs)
- [Practitioner/expert opinion] On its optional "Student must verify" setting (the student's input is "presented back to them before scoring as part of a two-step validation process"), STACK's authors write: "Experience strongly supports the use of this two-step verification process. Errors will always be displayed and expressions with errors rejected as invalid. Potential response trees will not execute with invalid input." No study is cited for this — [STACK docs, Inputs](https://docs.stack-assessment.org/en/Authoring/Inputs)
- [Practitioner/expert opinion] STACK echoes the student's expression "in traditional two-dimensional notation", and lists the variables found in it because, "From experience, this is helpful in letting students understand the idea of variable and to spot case insensitivity or wrong variable problems." — [STACK docs, Inputs](https://docs.stack-assessment.org/en/Authoring/Inputs)
- [Practitioner/expert opinion] STACK's student FAQ gives the philosophy: "students should not be penalized for poor computer syntax. It is better to bug students until their answer is unambiguous" than to risk marking them wrong for typing "sinx" and having it read as s*i*n*x (this is the case MATH-6 handles) — [STACK docs, student FAQ](https://docs.stack-assessment.org/en/Students/FAQ/)
- [Practitioner/expert opinion] STACK on implicit multiplication: "It is often very important to have some on-screen representation of multiplication, e.g. as a dot, so the student can see at the validation that" xe^x is read one way rather than another (the same idea as the explicit multiplication in MATH-6) — [STACK docs, input syntax](https://docs.stack-assessment.org/en/Authoring/Inputs/Input_syntax/)
- [Practitioner/expert opinion] STACK can mark floating-point input invalid (for example 0.5x^2+0.33 typed when 1/2*x^2+1/3 was meant) and can check the answer's type (an equation, not an expression) before scoring — the same idea as the "expected an interval" shape errors in the spec — [STACK docs, Inputs](https://docs.stack-assessment.org/en/Authoring/Inputs)
- [Observational/platform data] Sangwin (2003), University of Birmingham, Maple-based AIM system, about 190 first-year students on a randomly parameterised integration question: 34% made an error on their first attempt. The error table has a category called "syntax error", defined as an answer that is syntactically valid "but … not what the student probably meant", for example `4/9*x^9/4` typed for (4/9)x^(9/4), where the author notes "we know what the student meant"; the table lists 16 responses under this heading and 19 under "other", and the paper says only three specific error forms occur often enough to be worth targeted feedback — [Sangwin 2003, BSRLM Proceedings 23(3)](https://bsrlm.org.uk/wp-content/uploads/2016/02/BSRLM-IP-23-3-10.pdf)
- [Practitioner/expert opinion] WeBWorK added MathQuill because "Students don't always understand the difference it makes when writing 1/x+5 instead of 1/(x+5), or -5^2 instead of (-5)^2"; the editor "represents the expression clearly in real-time", a sidebar shows structures students struggle with (fractions, roots, exponents), and everything can be done by keyboard ("Starting with a / , we would have created the fraction object. Typing 7^11 would have created the exponent object … use our mouse or the direction keys to navigate") — [WeBWorK project, MathQuill](https://openwebwork.org/mathquill/)
- [Observational/platform data] Isaac Physics (Cambridge): 343 questions answerable either with the "Inequality" symbolic editor or the old numeric/multiple-choice format, over 472,000 attempts: students were equally proficient with both, and 72.9% of questions needed fewer attempts in symbolic format (the authors note multiple-choice invites guessing because wrong tries are not penalised). Note the comparison is symbolic editor versus multiple-choice/numeric, not editor versus typed syntax — [Franceschini, Sharkey & Beresford, L@S 2019](https://www.cl.cam.ac.uk/~arb33/papers/FranceschiniSharkeyBeresford-InequalityWebEquationEntry-LearningAtScale2019.pdf)
- [Observational/platform data] Same study, survey of 563 valid respondents (685 received, 122 discarded): 76.1% tend to avoid symbolic questions and 76.0% do not enjoy the equation editor; overall attitude negative, with comments that "seem to come from frustration with the system rather than prejudice against symbolic work", worst on small screens and with complex formulae; some respondents wanted a choice between the graphical editor and text entry; 70.5% did not find the editor distracting from working out answers — [Franceschini et al. 2019](https://www.cl.cam.ac.uk/~arb33/papers/FranceschiniSharkeyBeresford-InequalityWebEquationEntry-LearningAtScale2019.pdf)
- [Observational/platform data] Same paper: the system includes a text answer box whose content is parsed (a SymPy-based parser) and rendered "as the user types, thus providing immediate feedback", and lets users move between text and graphical entry; the authors also observe that template-based editors require students "to plan the expression ahead of entering it" and make rearranging parts cumbersome, and say the survey issues were addressed in a later update — [Franceschini et al. 2019](https://www.cl.cam.ac.uk/~arb33/papers/FranceschiniSharkeyBeresford-InequalityWebEquationEntry-LearningAtScale2019.pdf)
- [Observational/platform data] Bodnarchuk et al. (2026), two non-randomised cohorts (82 students on a pattern-matching Moodle test, 89 on a STACK test): the pattern-matching test needed 25 manual score corrections and had 4 responses it could not evaluate for input-related reasons, the STACK test needed 2 corrections and had 1; the authors call it a comparative description, not causal evidence. This is about answer checking rather than the preview, but it shows how much a tolerant checker matters — [arXiv 2607.11382](https://arxiv.org/abs/2607.11382) and [full text](https://arxiv.org/pdf/2607.11382)

#### Evidence: equation editor versus linear syntax versus handwriting
- [Lab study] Cummins et al. (2015), 22 undergraduates: a drag-and-drop editor ("Equality") took longer than Microsoft Equation Editor (mean 398 s versus 270 s per task set), needed many more mouse clicks (198 versus 83) but far fewer keystrokes (42 versus 201); participants found it easier to modify equations but showed no significant difference in preferred system, and the authors report that "the lack of keyboard support in our prototype was a large impediment to fluency" — [Cummins et al., ICALT 2015](https://www.cl.cam.ac.uk/~acr31/pubs/cummins-equality.pdf)
- [Lab study] Anthony, Yang & Koedinger (CMU, 2004-2008, summarised on the project page): for calculus-level expressions, handwriting was faster than typing in Microsoft Equation Editor "by a factor of 3" and was rated higher; algebra students using handwriting reached similar pre-to-post learning gains in about half the time of keyboard students; performance during practice predicted test performance better when the input modality matched the test's. Handwriting recognition accuracy was a limit (tutor context added about 10 percentage points) — [Anthony project page](https://www.cs.cmu.edu/~lanthony/research/multimodal/index.html)
- [Lab study] Knauff & Nejasmic (2014), 40 researchers writing documents with equations in Word or LaTeX: LaTeX users were slower, wrote less and made more errors, and expert LaTeX users did worse than novice Word users on most measures, though LaTeX users more often reported enjoying their software. Indirect evidence (document preparation, not answer entry) that linear markup carries a performance cost — [PLOS ONE 9(12): e115069](https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0115069)
- [Vendor docs] MathTOUCH authors (Mukogawa Women's University): "text-based mathematical input interfaces of e-assessment systems are cumbersome for novice learners"; their interface lists WYSIWYG candidate expressions as the student types; a field survey in one remedial class (20 junior-high students) found 85% thought the drill system more fun than learning on paper (a small, self-reported result, authors' own system) — [EAMS 2016 talk abstract](https://eams.ncl.ac.uk/archive/2016/session/mathtouch-mathematical-input-interface-in-e-assessment-systems)

#### MathLive behaviour and keyboard-only entry
- [Vendor docs] MathLive inline shortcuts replace typed sequences (typing P then I inserts the \pi symbol); "If a substitution was undesirable, use Undo (Control/Command/⌘ + Z) to revert to the raw input"; "To prevent two consecutive characters to be recognized as part of a shortcut sequence, press the Space bar between them"; the timing window for shortcuts is configurable — [MathLive, keybindings and inline shortcuts](https://mathlive.io/mathfield/guides/shortcuts/)
- [Vendor docs] MathLive's default key bindings include Alt/Option combinations (Alt/Option + V inserts a square root) — [MathLive shortcuts](https://mathlive.io/mathfield/guides/shortcuts/)
- [Vendor docs] MathLive on international keyboards: "Correctly handling keyboard shortcuts while accounting for non-US keyboard layout is surprisingly difficult. The mathfield element uses some heuristics that may occasionally result in surprising results"; there is no widely supported web API for the keyboard layout, the field guesses from the locale, and "If you happen to use an unknown keyboard layout, it will guess the wrong keyboard layout" — [MathLive shortcuts](https://mathlive.io/mathfield/guides/shortcuts/)
- [Standard/guideline] Apple advises "Use the Option modifier sparingly for less-common commands or power features" and warns that some languages need modifier keys to generate characters (Option-5 gives "{" on a French keyboard) — [Apple HIG, Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards)
- [Vendor docs] MathLive shows its virtual keyboard automatically only on touch-enabled devices (policy "auto"); "manual" leaves it to the app — [MathLive virtual keyboard guide](https://mathlive.io/mathfield/guides/virtual-keyboard.md)
- [Standard/guideline] WCAG 2.1.2 No Keyboard Trap (Level A): if focus can be moved to a component with a keyboard, it must be possible to move it away with a keyboard, and if that needs more than unmodified arrow or Tab keys the user must be told how — [W3C Understanding 2.1.2](https://www.w3.org/WAI/WCAG22/Understanding/no-keyboard-trap.html)

#### Competitor patterns worth copying
- [Practitioner/expert opinion] STACK: separate validation step with 2-D echo, variable list, "Insert stars" options for implicit multiplication, syntax hint inside the box, forbid-floats and type checks — [STACK docs, Inputs](https://docs.stack-assessment.org/en/Authoring/Inputs) and [Insert Stars](https://docs.stack-assessment.org/en/Authoring/Inputs/Input_syntax/)
- [Practitioner/expert opinion] WeBWorK MathQuill: live 2-D rendering, structure sidebar, hover text showing the typed shortcut ("inf" for infinity), raw-text button for units — [WeBWorK MathQuill](https://openwebwork.org/mathquill/)
- [Observational/platform data] Isaac Physics: structured editor plus text box with live render and conversion between them — [Franceschini et al. 2019](https://www.cl.cam.ac.uk/~arb33/papers/FranceschiniSharkeyBeresford-InequalityWebEquationEntry-LearningAtScale2019.pdf)
- [User reports] Math Academy users reported that multiple-choice selection of complex formulas was error-prone and could not be undone (carried) — [prior_art_and_ux.md](/docs/research/notes/Toishi%20build%20research/prior_art_and_ux.md)

### Inferences
#### Verdicts
- Preview of the parsed answer, plus "invalid is not an attempt" (MATH-6, answering step 2): **Supported** by consistent practitioner experience (STACK, WeBWorK, Isaac) and by an observed error class that a preview exposes (Sangwin's 16 precedence misreads); strength is expert opinion plus observational data, with no controlled measurement of false rejects avoided.
- Math field as the default with a plain-text alternative: **Weakly supported**. Isaac's survey shows friction drives avoidance and that users asked for a choice, and Isaac's system pairs its editor with a live-rendered text box, which is the same shape as this design; no study says which should be the default for a keyboard user. Cummins suggests keyboard-first entry beats mouse-first palettes on a desktop.
- Shape helpers (MATH-7): **Weakly supported** by analogy to STACK's type checks and the WeBWorK structure sidebar; no direct test.
- Choosing MathLive: **Missing** evidence. The only material found is MathLive's own documentation; there is no independent usability or learning-curve study. The choice is defensible on features (keyboard shortcuts, offline speech, MIT licence) rather than evidence.
- Keyboard-only maths entry on a Mac (dead keys, Option shortcuts, IME, non-US layouts, paste, escaping the field with Tab): **Missing**; MathLive's own docs list the heuristics as a known weak point and the backlog lists these as unchecked.

#### Recommendations
1. Treat the answer box as the top usability risk and test it first in the DEV-15 think-aloud rounds with a scripted set of typed answers (fractions, powers, roots, intervals, trig, `log`), measuring time to enter, number of preview corrections, and invalid rate per answer type. The app already stores attempts, so log first-attempt invalid rate by answer type and by mode to find the worst offenders (the Sangwin approach).
2. Keep the preview rendering real fraction bars and exponents rather than slashes and carets, because the `4/9*x^9/4` class of error is only visible when precedence is drawn; this is most important in plain-text mode, where precedence ambiguity actually lives. In the math field the structure is explicit by construction.
3. Test, and document in the tutorial, MathLive's inline-shortcut substitutions (pi, in, and the like) and how to undo them; consider disabling shortcuts the curriculum never needs, as the `log` override already does.
4. Before 1.0, run the unchecked backlog items and add: Option-key and dead-key input, a non-US layout (and an input method), paste of LaTeX and of plain text, Tab and Shift+Tab out of the field, and key repeat. If any Alt/Option binding collides with typed characters, remove the binding.
5. Offer a short in-context "how to type this" help (for the current answer type) reachable from the answer box, because the best precedent systems (STACK, WeBWorK) show syntax hints and shortcut text where the student is typing.
6. Handwriting or trackpad drawing is the fastest modality in the one lab programme found but is out of scope for a keyboard-first desktop app; revisit only if a touch device is added.

### Gaps
- No controlled study was found that measures the reduction in false rejects from a preview step, or from "invalid is not an attempt"; STACK's claim rests on authors' experience. Searching for such a study was cut off by the search budget.
- No independent evidence on MathLive usability or learning curve, and the MathLive/KaTeX GitHub issue trackers could not be read in this session (GitHub access was disabled), so known open bugs are unknown.
- Input specifics for Möbius/Maple TA, MyLab/MyMathLab, DeltaMath and WebWork's newer editors were not retrieved; the competitor list above is therefore limited to STACK, WeBWorK, Isaac Physics, MathTOUCH and carried Math Academy notes.
- The MathTOUCH result rests on a conference abstract only (the follow-up MSOR Connections paper pages returned no text), so its design and survey details are unverified.
- No data on how often students mistype versus misunderstand notation when a WYSIWYG field removes precedence ambiguity; the Sangwin and WeBWorK arguments predate WYSIWYG fields in most deployments.
- Whether VoiceOver can operate a MathLive field inside a WKWebView window is not documented in anything retrieved (see section 7).


## 2. Session design: what does the evidence say about session length and breaks, end-of-session summaries, daily goals, forgiving streaks and the "Lighter set"?

### Takeaway
Task-based daily goals have field-experiment support, forgiving streaks have indirect support (habit research, company data, one RCT of streak messaging), and optional breaks have support for mood and fatigue rather than for performance. The specific choices (a reminder at 50 minutes, a 20-second eye rest, the end-of-session summary, the Lighter set rules, the freeze-earning rule) have no direct evidence and should be treated as reasonable defaults to measure.

### Cited Findings

#### Current design (spec IDs)
- [Local file] Break reminder every 50 minutes (setting: Off, or 25 to 90) that "suggests standing up and looking at something far away for 20 seconds. It never interrupts a problem" — [spec.md, "Design and theme", Long sessions, and the Settings table](/docs/spec.md)
- [Local file] TIME-1 pause (button, Esc or P) stops the clock and blurs the problem; TIME-2 auto-pause on focus loss, app switch, screen lock or sleep; TIME-3 no pause on input inactivity because the work happens on paper, but after three times the target time (at least 5 minutes) a quiet "Still working?" note appears and, with no answer in 60 seconds, the clock pauses and trims back; TIME-6 an Untimed switch — [spec.md](/docs/spec.md)
- [Local file] Daily problem count chosen at first run (default 20, projected minutes shown beside it); Home shows today's problems with projected minutes (QUE-3, STA-1) and never an overdue count (QUE-7) — [spec.md](/docs/spec.md)
- [Local file] QUE-10 "Lighter set": keeps today's due skills but serves tier 1 and 2 problems and adds no new skills, successes count as Hard; QUE-17 "Back from a break": after 3 or more missed days Home offers "Back on track by <date> at N a day" with three paces; QUE-15 undo last answer; QUE-16 resume after a quit or crash — [spec.md](/docs/spec.md)
- [Local file] STA-1 forgiving streak: any study keeps it; at most 2 freezes, earning 1 per 7 days with the daily set done; a freeze covers a missed day automatically; with none left, the streak survives a missed day if the next 2 days' sets are both done — [spec.md](/docs/spec.md)
- [Local file] End of session: a summary lists problems done, time, misses with their tags and skills learned, plus tomorrow's forecast; "Extra practice" is offered, never pushed; "Practice test" appears when an exam is within 21 days (QUE-18) — [spec.md, "End of session"](/docs/spec.md)
- [Local file] Hand-test defects on this screen: the summary said "Tomorrow: 4 problems" while Home offered 4 more today, the "To revisit" list repeated a skill, and Pause showed on the summary (the first two were addressed in ADR-0018) — [backlog.md items 5 and 7](/docs/backlog.md) and [ADR-0018](/docs/decisions/0018-hand-test-fixes.md)

#### Evidence: breaks, fatigue and test-interleaving
- [Meta-analysis/review] Albulescu et al. 2022 (19 records, 22 independent samples, N = 2,335): micro-breaks gave small significant gains in vigor (d = .36, k = 9) and lower fatigue (d = .35, k = 9) but a non-significant effect on performance (d = .16, p = .116, k = 15); performance effects were significant only for tasks with lower cognitive demand; "the longer the break, the greater the boost was on performance"; for highly depleting tasks "recovering … may need more than 10-minute breaks" — [PLOS ONE 17(8): e0272460](https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0272460)
- [Field experiment] Biwer et al. 2023, 87 university students studying for one day: self-regulated breaks (n = 35) versus a 6-minute break after each 24-minute block ("Pomodoro", n = 25) versus a 3-minute break after each 12-minute block (n = 27). Self-regulating students had longer sessions and breaks, more fatigue and distractedness, and lower concentration and motivation; there was no difference in invested mental effort or task completion; the authors conclude systematic breaks had mood benefits and "appeared to have efficiency benefits" (similar completion in less time). The abstract does not say how students were assigned — [Biwer et al., Br J Educ Psychol 93(S2)](https://cris.maastrichtuniversity.nl/en/publications/understanding-effort-regulation-comparing-pomodoro-breaks-and-sel)
- [Observational/platform data] Sievertsen, Gino & Piovesan 2016, all Danish public-school test results 2009/10 to 2012/13: for every hour later in the day, performance fell by 0.9% of an SD (95% CI 0.7-1.0%), and a 20 to 30 minute break raised average performance by 1.7% of an SD (95% CI 1.2-2.2%) — [PNAS 113(10), Bristol repository record](https://research-information.bris.ac.uk/en/publications/cognitive-fatigue-influences-students-performance-on-standardized/)
- [Lab study] Szpunar, Khan & Schacter 2013, two experiments: interpolating online lectures with memory tests reduced mind-wandering, increased note-taking, improved learning, and reduced test anxiety and subjective cognitive demand (lectures, not problem practice) — [PNAS, PMC3631699](https://pmc.ncbi.nlm.nih.gov/articles/PMC3631699/)
- [Field experiment, before-and-after design; the abstract describes no control group] Talens-Estarelles et al., 29 symptomatic computer users given software that reminded them of the 20-20-20 rule for two weeks: digital eye strain and dry-eye symptoms fell (p ≤ 0.045) but the gain was not maintained a week after reminders stopped (p > 0.05); binocular and tear-film signs were largely unchanged — [Aston Research Explorer record](https://research.aston.ac.uk/en/publications/the-effects-of-breaks-on-digital-eye-strain-dry-eye-and-binocular/)

#### Evidence: habits, streaks and forgiveness
- [Observational/platform data] Lally et al. 2010, 96 volunteers repeating one behaviour daily for 12 weeks: time to reach 95% of asymptotic automaticity ranged from 18 to 254 days, and "Missing one opportunity to perform the behaviour did not materially affect the habit formation process" — [Eur J Soc Psychol 40(6), abstract via Crossref](https://api.crossref.org/works/10.1002/ejsp.674)
- [Company A/B or company data] Duolingo (Osman Mansur, 13 May 2024): learners with a 7-day streak are 3.6 times more likely to complete a course (no method given, so an association rather than a tested effect); allowing up to 2 streak freezes at once raised daily active learners by 0.38%; a milestone animation raised 7-day retention of new learners by 1.7%; the post argues a streak that vanishes after one missed day can demotivate — [Duolingo blog, streak research (Japanese edition fetched; figures match the English post cited in earlier notes)](https://blog.duolingo.com/duolingo-streak-research/)
- [RCT] Aulagnon, Cristia, Cueto & Malamud 2025: 60,000 Peruvian 4th-6th graders randomised to streak-highlighting messages, personalised reminders, generic reminders or control; highlighting streaks and personalised reminders raised use of an online maths platform versus generic reminders and control, and highlighting streaks improved maths achievement versus control among the 1,500 students who took an endline test, though differences with the other arms were not significant — [NBER w34173](https://www.nber.org/papers/w34173)
- [Meta-analysis/review; carried] Sailer & Homner 2020 gamification meta-analysis: cognitive g = .49, motivational g = .36, behavioural g = .25, with the motivational and behavioural effects non-significant in the most rigorous designs — [science_of_practice.md, carried](/docs/research/notes/Practice%20systems%20and%20learning%20science/science_of_practice.md)

#### Evidence: daily goals
- [Field experiment] Clark, Gill, Prowse & Rush 2017, two field experiments with almost 4,000 college students: goals for a particular task (completing online practice exams) "had large and robust positive effects on the level of task completion" and raised course performance, the extra task completion causing the extra performance; goals for performance had positive but small effects — [NBER w23638](https://www.nber.org/papers/w23638)
- [Vendor docs] Math Academy FAQ (vendor copy; the page still mentions a "Beta Group"): the daily XP goal and work days per week are adjustable, "we strongly recommend reasonable and regular practice of 20 to 40 XP per day, 3 to 5 days per week", and "anything less than 3 days per week would not be recommended" — [Math Academy FAQ](https://www.mathacademy.com/faq)

#### Evidence: summaries and framing
- [Vendor docs] Anki's manual says of its statistics: "The stats for the current day are not a good overall indicator of your learning progress; everyone has bad days" — [Anki manual, Statistics](https://docs.ankiweb.net/stats.html)
- [Meta-analysis/review] Shute 2008 reports that, according to researchers, formative feedback should be "nonevaluative, supportive, timely, and specific" — [Review of Educational Research 78(1), abstract via Crossref](https://api.crossref.org/works/10.3102/0034654307313795)

#### Competitor patterns
- [Vendor docs] Anki "Easy Days": "If you want to spend less time on Anki on some days of the week, such as Sundays, this feature can help you do that"; it shifts future intervals slightly and is not retroactive (the spec's Easy days setting is the same idea) — [Anki manual, Deck Options](https://docs.ankiweb.net/deck-options.html)
- [Vendor docs] Anki keys: Space or Enter shows the answer and then picks Good; 1-4 pick a specific button; "Many people find it convenient to answer most cards with Space and keep one finger on 1 for when they forget" — [Anki manual, Studying](https://docs.ankiweb.net/studying.html)
- [Vendor docs; carried] UWorld: tutor mode (answer and rationale after each question, for the first pass) versus timed mode (random 40-question blocks, for the second pass); UWorld's blog suggests 60-120 questions a day over 4-8 weeks for a second pass, and the earlier notes found no study comparing the modes for learning outcomes — [practice_platforms.md section 7, carried](/docs/research/notes/Practice%20systems%20and%20learning%20science/practice_platforms.md)

### Inferences
#### Verdicts
- Break reminder at 50 minutes with a 20-second eye break (spec "Long sessions"): **Weakly supported**. Breaks help mood and fatigue (d about .35) and structured breaks beat self-chosen ones for concentration in one small study, but the performance effect is not reliable and nothing tests 50 minutes. The 20-second "look far away" is the 20-20-20 eye-rest idea, whose only evidence here is a 29-person uncontrolled study. The reminder is harmless because it is optional and never interrupts a problem.
- Daily goal as a problem count: **Supported** by Clark et al. (task-based goals), with the caveat that those students had a course and an instructor.
- Forgiving streak and no overdue count (STA-1, QUE-7): **Weakly supported** but directionally consistent with Lally (a single miss is harmless), Duolingo's data on freezes, and the Peru RCT; the earn-one-freeze-per-seven-days and survive-if-next-two-days rules are the app's own and have no source.
- Lighter set (QUE-10): **Weakly supported** only by analogy to Anki's Easy Days; whether students use it, and whether counting successes as Hard keeps the schedule honest, is an engine question for the validation plan.
- End-of-session summary and forecast: **Unsupported** in the sense that no evidence was found either way; low risk. Shute's guidance (specific, supportive, non-evaluative) is the nearest standard, and the hand-test defect (summary and Home disagreeing on what is left today) shows the real cost is inconsistency.

#### Recommendations
1. Keep the break reminder optional and Off-able, but reword it to offer two cues (eyes: look away for 20 seconds; fatigue: a few minutes away from the desk), since the meta-analysis links performance gains to longer breaks; log whether it is dismissed or snoozed before tuning the 50-minute default.
2. Present the daily goal as a count of problems (task-based) and the minutes as a projection, which is already the design.
3. Treat the streak and freeze numbers as tunable defaults; log how often a freeze or the two-day rule is used and whether study resumes afterward.
4. Make the summary and Home read from one source of truth for "what is left today" so the two cannot disagree.

### Gaps
- No study was found on session length for self-paced, spaced problem practice, on break reminders in such tools, or on the 50-minute/20-second combination specifically.
- No empirical study of end-of-session summaries or "tomorrow" forecasts; the nearest datum is Duolingo's 1.7% effect of a milestone animation, which says nothing about summaries.
- Wilson et al. 2019's "85% rule" is a learning-theory result for gradient-descent-type learners ([Crossref abstract](https://api.crossref.org/works/10.1038/s41467-019-12552-4): derived for stochastic gradient-descent-based learning algorithms and demonstrated on artificial neural networks and biologically plausible neural networks), and no human-learner confirmation was retrieved; it bears on difficulty targeting more than on session length.
- Duolingo's streak and freeze figures come from company posts without methods; the page fetched was the Japanese edition, used only for the figures.
- Clark et al. studied college students with an instructor-set course; transfer to self-directed adult learners is untested here.

## 3. Onboarding: what does the evidence say about time to first value, placement-test UX, and goal-setting or planning prompts?

### Takeaway
The first-run flow meets the three conditions in which Nielsen Norman Group says onboarding is justified (needs user information, tailored behaviour, an unusual input workflow), but six steps before the first problem conflicts with Apple's "postpone nonessential setup" and NN/g's "avoid onboarding whenever possible". The LIB-12 claim that a written if-then plan is "the one tested way to raise practice volume" is not supported: one small RCT is positive, large-scale tests were null, and other tested interventions exist.

### Cited Findings

#### Current design (spec IDs)
- [Local file] First run in six steps: (1) profile, name only; (2) theme (Automatic default) and daily count (default 20, minutes shown); (3) subjects, goal and goal date, known exams, section states; (4) study plan (LIB-12: when and where, likely obstacle, if-then plan); (5) placement test, "the default first session", skippable or pausable, seeding each skill and the first Weak areas list; (6) Answer Input Tutorial deck, "a few minutes practicing how to type fractions, roots, intervals and points" — [spec.md, "First run"](/docs/spec.md)
- [Local file] Placement check: one standard-tier problem per skill starting from the most advanced, a pass marks prerequisites provisionally known, every question has an "I don't know" button, it can be skipped, paused, resumed and re-run, stops after 25 questions per course, a directly passed skill starts with provisional stability of about 10 days and an inferred one about 2.3 days, and "Placement only ever adds knowledge. It never takes progress away." — [spec.md, "Placement check"](/docs/spec.md)
- [Local file] LIB-12 ends with "A written if-then plan is the one tested way to raise practice volume in exam prep"; Home shows the plan again after two missed days — [spec.md LIB-12](/docs/spec.md)
- [Local file] M8 exit criterion: "A new profile goes from first launch to first session in under 5 minutes; placement stays within 25 questions" — [spec.md, milestone table](/docs/spec.md)
- [Local file] Sequencing note: the tutorial (step 6) comes after the placement test (step 5), although placement answers are typed in the same math field, and the spec says the placement test can be skipped but does not say the tutorial can — [spec.md, "First run"](/docs/spec.md)

#### Evidence: when onboarding is warranted, and how long
- [Practitioner/expert opinion, with internal research] NN/g (Kendrick 2020, mobile apps): onboarding has a higher interaction cost, strains memory, and "may not improve user performance" (their research on deck-of-cards tutorials "showed that tutorials didn't improve task performance"); "we recommend professionals avoid creating app onboarding whenever possible"; screens are useful when the app needs user information to start, is "highly tailored to the user's context and preferences", or has workflows that are "fairly unique to the app"; contextual tips are preferred, and teams should "test the app with no onboarding" first — [NN/g, Mobile-App Onboarding](https://www.nngroup.com/articles/mobile-app-onboarding/)
- [Standard/guideline] Apple HIG: "Postpone nonessential setup flows or customization steps. Provide reasonable default settings so most people can immediately start interacting"; "Teach through interactivity"; "If it makes sense to offer a separate tutorial, consider making it optional … make sure it's easy for people to find if they want to view it later"; a prerequisite flow should be "brief" and not require memorising much; prefer context-specific tips to one flow — [Apple HIG, Onboarding](https://developer.apple.com/design/human-interface-guidelines/onboarding)
- [Standard/guideline] Apple HIG: "Avoid using settings to ask for setup information you can get in other ways", for example whether people are using Dark Mode — [Apple HIG, Settings](https://developer.apple.com/design/human-interface-guidelines/settings)
- [Standard/guideline] Apple HIG: "Restore the previous state when your app restarts so people can continue where they left off" (the resume behaviour QUE-16 follows this) — [Apple HIG, Launching](https://developer.apple.com/design/human-interface-guidelines/launching)
- [Observational/survey] Acosta-Gonzaga & Walet (University of Manchester), survey of first-year STEM students who had all been exposed to online assessment with substantial mathematical work: "even for this digital generation, confidence in using computers and the availability of support for using information technology are important factors in making effective use of on-line assessments"; attitude and enjoyment were the two strongest influences on intention to use — [Acosta-Gonzaga & Walet, arXiv 1603.02313](https://arxiv.org/abs/1603.02313)

#### Evidence: placement tests
- [Vendor docs; carried] ALEKS's initial Knowledge Check uses "approximately 20-30 questions", gives no right/wrong feedback during the check, offers an "I Don't Know" choice, can be resumed after logout and cannot be bypassed at first login; later progress checks can push topics back, which users describe as punitive — [McGraw Hill, What is an ALEKS Knowledge Check?](https://www.mheducation.com/support/aleks-support-center/knowledge/what-is-a-knowledge-check.html) and [prior_art_and_ux.md, carried](/docs/research/notes/Toishi%20build%20research/prior_art_and_ux.md)
- [Meta-analysis/review; carried] A meta-analysis of 15 studies (24 samples, 2005-2015) found ALEKS "as good, but not better than, traditional classroom teaching", with larger effects for shorter durations of use — [Fang, Ren, Hu & Graesser 2019](https://digitalcommons.memphis.edu/facpubs/7254), via [prior_art_and_ux.md, carried](/docs/research/notes/Toishi%20build%20research/prior_art_and_ux.md)
- [Vendor docs] Math Academy's FAQ: its adaptive diagnostic assessment "will identify the correct starting place for the student, wherever that is"; the student receives a diagnostic report with a course recommendation and estimated completion dates for example daily XP paces — [Math Academy FAQ](https://www.mathacademy.com/faq)
- [User report; carried] One Math Academy user's first-month report (a reader submission on the FSRS author's Substack) said that correcting a wrong placement by deliberately failing was slow and cost XP, and suggested an explicit "I don't know this topic" option, which the report says Math Academy declined for fear of misuse — [My First Month with Math Academy](https://lmsherlock.substack.com/p/my-first-month-with-math-academy), via [prior_art_and_ux.md, carried](/docs/research/notes/Toishi%20build%20research/prior_art_and_ux.md)

#### Evidence: goal-setting and planning prompts
- [Field experiment] Clark et al. 2017 (task-based goals, almost 4,000 students): large positive effects on task completion and course performance — [NBER w23638](https://www.nber.org/papers/w23638)
- [Field experiment] Yeomans & Reich 2017, three HarvardX courses: open-ended planning prompts at course start raised completion by 29% and payment for certificates by 40%; the effect was largest for students in traditional schools, and plans that "focused on specific times" predicted non-completion — [MIT DSpace](https://dspace.mit.edu/handle/1721.1/137973)
- [Field experiment, preregistered, large-scale] Kizilcec et al. 2020, 247 online courses and 269,169 students (the authors' phrase is "one-quarter million"): the hypothesis of medium-to-large effects "is not supported"; the earlier plan-making result (29% more completion, from 14% to 18%, in three courses with n = 2,053) did not replicate (long-term planning prompts for committed English-fluent students: +0.19 percentage points in year 1, 95% CI -0.69 to 1.07; -0.23 in year 2, CI -1.61 to 1.14); the mental-contrasting-plus-implementation-intentions (MCII) arm did not improve completion for students in individualistic countries (+0.25 pp, CI -0.87 to 1.37); plan-making slightly raised engagement in the first weeks but its benefits "dissipated over the span of a full course"; scaling "can reduce their average effectiveness by an order-of-magnitude" — [PNAS, PMC7334459](https://pmc.ncbi.nlm.nih.gov/articles/PMC7334459)
- [Field experiment] Oreopoulos & Petronijevic 2019, about 25,000 students at three campuses: coaching-style online and text interventions improved mental health and study time somewhat, but "none of the interventions we evaluate significantly influences academic outcomes"; students study about five to eight hours fewer per week than they plan, and the interventions did not change this — [NBER w26059](https://www.nber.org/papers/w26059)
- [RCT; carried] Duckworth et al. 2011: 66 second-year high-school students, one selective school; a 30-minute written exercise (outcomes, obstacles, if-then plans, where and when to work) versus an unrelated essay; practice questions completed in a summer PSAT workbook about 140 versus about 84, beta = 0.27, p = 0.04; the earlier notes record no replication — [Duckworth et al. 2011 via science_of_practice.md](https://www.socmot.uni-konstanz.de/sites/default/files/duckworth_self-regulation_11.pdf)

### Inferences
#### Verdicts
- LIB-12 sentence "the one tested way to raise practice volume": **Unsupported as worded**. At least four lines of evidence disagree with "the one": a small positive RCT (Duckworth), a positive three-course field experiment (Yeomans & Reich), null large-scale replications (Kizilcec, Oreopoulos), and a different tested lever (task-based goals, Clark et al.). A plan screen is cheap and plausible, but the defensible claim is "mixed evidence".
- Six-step first run before the first problem: **Weakly supported, at odds with guidance on length**. Steps 3 (goals and exams), 5 (placement) and 6 (input tutorial) meet NN/g's criteria; step 2's theme question asks something the system can detect (HIG), and step 4 (plan) is nonessential and, per the replication evidence, low-yield, so it could wait until after the first session.
- Under-5-minutes target: **Missing** evidence for the number; a plausible target that should be measured in DEV-15, not assumed.
- Placement with "I don't know", a hard cap of 25 per course, skippable, "only adds knowledge": **Weakly supported**; it matches ALEKS's 20-30 question range and answers the main user complaints (punitive resets, no way to say "don't know").
- Answer Input Tutorial: **Weakly supported**. The input workflow is unusual (NN/g's third condition) and interactive teaching is what HIG recommends; the sequence (after placement) and the lack of an explicit skip are the weak points.

#### Recommendations
1. Move the input tutorial before the placement test (or open the placement with two or three warm-up items that teach the field), because placement results seed scheduling state and mistyped answers would be scored as "doesn't know"; make it skippable and re-openable from Help.
2. Drop the theme question from first run (Automatic is the default; the setting stays in Settings) and consider showing the study-plan prompt on Home after the first session or after two missed days, which the spec already does for reminders.
3. Replace the LIB-12 evidence sentence with a hedged one (for example, "planning prompts help some learners; evidence is mixed") and keep the plan optional and editable.
4. Show placement progress ("question 7, up to 25") and keep a visible "Finish now" so skipping is possible at any point.
5. Time the flow in the first usability round and record where users stall (course tree, exam entry).

### Gaps
- No benchmark for time to first value in learning apps was retrieved; the 5-minute target is the project's own.
- Duolingo's reported finding that delaying sign-up raises engagement could not be confirmed (the Taplytics page looped; the Lenny's article does not contain the claim).
- The NN/g article is about mobile apps (2020), not desktop learning software, and the deck-of-cards tutorial finding is their internal research with no sample size given in the text fetched.
- The Math Academy FAQ is vendor copy that gives recommendations without evidence; the ALEKS material is vendor documentation and user comments, not studies of placement-test length or abandonment.
- Gollwitzer & Sheeran's implementation-intention meta-analysis and Moreno/Mayer-style onboarding research were not retrieved; no evidence on if-then plans for adult self-study exam preparation was found beyond the sources above.
- Acosta-Gonzaga & Walet is an attitude survey of one university's first-year STEM students; it says nothing about onboarding length or placement tests, and is cited only for the role of computer confidence and support.


## 4. Stats dashboards: what does the evidence say about student-facing learning-analytics dashboards, and what do Anki, Math Academy, Duolingo and UWorld show?

### Takeaway
Systematic reviews of student-facing dashboards find no evidence that they raise achievement and some evidence that they raise participation, so each Stats view should be judged by whether it changes what the student does next, not by completeness. The best-supported design principle available is to report delayed retention rather than practice accuracy, which the spec already does (STA-3); STA-4's calibration and policy comparisons are developer validation, not student-facing content.

### Cited Findings

#### Current design (spec IDs)
- [Local file] Other screens share a left sidebar: Home, Study, Library, Browse, Stats, Settings — [spec.md, "Layout"](/docs/spec.md)
- [Local file] Home shows "Today: 20 problems, about 55 minutes" per active course with exam countdowns and "never shows an overdue count"; STA-1 adds the forgiving streak — [spec.md, intro and STA-1](/docs/spec.md)
- [Local file] The Stats views are: STA-2 forecast (7 and 30 days); STA-3 retention on delayed reviews against desired retention, with a one-line contrast of the student's own practice accuracy and later results ("92% during learning blocks, 81% on the same skills a week later"); STA-4 calibration (predicted against observed recall by bin) plus the shadow partial-credit comparison (ENG-7) and the triage-policy comparison (QUE-6); STA-5 skill map (one row per section, one cell per skill, Level and Recall); STA-6 exam readiness; STA-7 time per day and a calendar heatmap; STA-8 mistakes; STA-9 speed as a weekly trend labelled "exam-ready pace"; STA-10 goals; STA-11 weak areas; STA-12 readiness as an 80% range, never a single number; STA-13 lost-points report; STA-14 mistake states — [spec.md, "Stats"](/docs/spec.md)
- [Local file] Milestone M10 lists the dashboard with "Recall, Level, speed, goal and calibration views", with the exit criterion "Every setting changes behavior as specified; edits validate live and exports round-trip; contrast and keyboard checks pass" — [spec.md, milestone table](/docs/spec.md)
- [Local file] Hand-test defect: the end-of-session summary said "Tomorrow: 4 problems" while Home offered 4 more today (two screens disagreeing about the same count) — [backlog.md item 5](/docs/backlog.md)

#### Evidence: do student-facing dashboards change learning?
- [Meta-analysis/review] Kaliisa et al. 2024, systematic review of 38 studies: "there is no evidence to support the conclusion that LADs have lived up to the promise of improving academic achievement"; most studies reported negligible or small effects with limited well-powered controlled experiments; many studies "merely compared users and non-users of LADs, confounding the dashboard effect with student engagement levels"; effects on motivation and attitudes "appeared modest"; but "LADs showed a relatively substantial impact on student participation", with several studies reporting medium to large effects; recurring flaws were self-selection, "the assumption that access equates to usage", and a lack of standardized assessment tools — [Kaliisa et al., arXiv 2312.15042](https://arxiv.org/abs/2312.15042)
- [Meta-analysis/review] Bodily & Verbert 2017, review of student-facing learning-analytics reporting systems (945 articles retrieved, 93 included): experiments on effects on student behavior, achievement and skills are "needed to add to the small existing body of evidence", and studies should include usability tests and measures of how students actually use the systems — [Bodily & Verbert, IEEE TLT 2017](https://lirias.kuleuven.be/retrieve/467439)
- [Meta-analysis/review; read through a lab announcement, not the paper] A systematic review of empirical LAD studies from a self-regulated-learning perspective (Gasevic and colleagues, IEEE TLT) found existing LADs "rarely grounded in learning theory", that they "cannot be suggested to support metacognition", that they "do not offer any information about effective learning tactics and strategies", and that evaluation is limited in how it is conducted and reported — [Monash Digital Education Research lab, announcement](https://der.monash.edu/a-systematic-review-of-empirical-studies-on-learninganalytics-dashboards-a-self-regulated-learning-perspective/)
- [Standard/review; metadata only] Jivet et al.'s reviews "Awareness is not enough: pitfalls of learning analytics dashboards in the educational practice" (EC-TEL 2017) and "License to evaluate" (LAK 2018) are indexed with the keywords social comparison and competition, but only the bibliographic pages were retrievable, so no findings are recorded from them — [OU research portal, 2017 record](https://research.ou.nl/en/publications/awareness-is-not-enough-pitfalls-of-learning-analytics-dashboards/) and [OU research portal, 2018 record](https://research.ou.nl/en/publications/license-to-evaluate-preparing-learning-analytics-dashboards-for-e/)

#### Evidence: what a practice dashboard should show
- [Meta-analysis/review; carried] Soderstrom & Bjork 2015: performance during training is often an unreliable index of whether learning occurred, and learners often mistake current performance for lasting learning (the earlier notes record it as strong evidence) — [PubMed 25910388](https://pubmed.ncbi.nlm.nih.gov/25910388/), via [speed_mastery_goals.md, carried](/docs/research/notes/Toishi%20gaps%20research/speed_mastery_goals.md)
- [Lab study; carried] Yan, Bjork & Bjork 2016: across experiments 72% of learners judged blocked practice more effective than interleaving; only experience combined with an explanation moved a majority (75%, rising to 93% when interleaving was experienced first) — [Yan, Bjork & Bjork 2016](https://sites.lifesci.ucla.edu/psych-bjorklab/wp-content/uploads/sites/13/2016/11/YanBjorkBjork2016.pdf), via [learning_science.md, carried](/docs/research/notes/Toishi%20build%20research/learning_science.md)
- [Vendor docs] Anki's manual: "The stats for the current day are not a good overall indicator of your learning progress; everyone has bad days and good days"; for the True Retention table, "data for a single day is noisy, so it's better to look at monthly data"; with FSRS, true retention "is expected to be close to your desired retention" — [Anki manual, Statistics](https://docs.ankiweb.net/stats.html)
- [User report; carried] Math Academy: pace and ETA numbers that disagree across screens eroded one user's trust ("limited trust in the numbers") — [Hecker, part 10](https://frankhecker.com/2025/02/17/math-academy-part-10/), via [prior_art_and_ux.md, carried](/docs/research/notes/Toishi%20build%20research/prior_art_and_ux.md)

#### Competitor patterns
- [Vendor docs] Anki's graphs: Future Due (estimated reviews per day, with a shaded line for not studying), Calendar (past activity), Reviews, Review Time, Card Retrievability (FSRS only: "probability of recall", plus an estimated total-knowledge count), Hourly Breakdown, Answer Buttons, and a True Retention table that counts first review per day, Again as fail and Hard/Good/Easy as pass — [Anki manual, Statistics](https://docs.ankiweb.net/stats.html)
- [Vendor docs] Math Academy: the diagnostic report gives a course recommendation and estimated completion dates for example daily-XP paces, and the daily XP goal and work days per week are adjustable — [Math Academy FAQ](https://www.mathacademy.com/faq); the earlier notes (from its How It Works page) add per-topic mastery in the report and describe XP as "roughly equivalent to 1-minute of focused effort" — [prior_art_and_ux.md, carried](/docs/research/notes/Toishi%20build%20research/prior_art_and_ux.md)
- [User reports; carried] Math Academy and Duolingo points systems: XP rewarded speed over depth for some users; a leaderboard produced a 4.5-hour session worth 76 XP; leagues encouraged "XP for its own sake" so one user turned them off; a Duolingo columnist wrote that XP boosts made them "rush through the lesson to score XP and climb the leaderboard" — [prior_art_and_ux.md, carried](/docs/research/notes/Toishi%20build%20research/prior_art_and_ux.md) and [Android Authority opinion](https://androidauthority.com/duolingo-xp-boost-ux-trap-3674572)
- [Vendor docs; carried] UWorld: a Performance section with Overall, Reports by subject, system and topic, and Graphs by date and by test; after each answer the percentage of students choosing each option; an overall percentile and average time per question versus other users — [UWorld USMLE features](https://medical.uworld.com/usmle/features/), via [practice_platforms.md section 7, carried](/docs/research/notes/Practice%20systems%20and%20learning%20science/practice_platforms.md)
- [User reports; carried] Student Doctor Network posters (a 2016 thread) mostly said UWorld percentages are a weak predictor of the real score ("Use it to learn. Ignore the percentages") — [Student Doctor Network thread](https://forums.studentdoctor.net/threads/uworld-average.1186593/post-17536393), via [practice_platforms.md, carried](/docs/research/notes/Practice%20systems%20and%20learning%20science/practice_platforms.md)
- [User reports; carried] Anki users cite review pile-ups after missed days and the lack of a vacation mode as major pain points — [Capterra reviews](https://www.capterra.com/p/229584/Anki/reviews/), via [prior_art_and_ux.md, carried](/docs/research/notes/Toishi%20build%20research/prior_art_and_ux.md)

### Inferences
#### Verdicts
- A student Stats screen at all: **Weakly supported**. No review finds that dashboards raise achievement; the one reasonably consistent effect is on participation. The case for these views is therefore about honest self-monitoring and planning (forecast, goal pace), not about learning gains, and should be tested by whether the view changes behaviour.
- STA-3 (delayed retention, with the own-data contrast): **Weakly supported**. The principle (practice accuracy misleads; delayed performance is the better index) is well supported by Soderstrom & Bjork, and Yan et al. found that experience plus an explanation is what changes beliefs, which matches the one-line contrast. No study tests this specific display.
- STA-4 (calibration bins, shadow partial credit, triage-policy comparison) on the student Stats screen: **Unsupported**. No source suggests that students use or understand calibration plots; these are validation instruments for the developer, and the spec lists them in the same milestone as the student views (M10).
- STA-12 (80% score range instead of a point estimate): **Missing** evidence on how students read ranges; the spec's own rationale is that single-test predictions miss by about 7 points. Treat the wording as a usability-test item.
- STA-9 (speed as a weekly trend, "exam-ready pace"): **Unsupported** either way; the carried user reports of XP rewarding speed over depth are a caution about how speed is framed.
- No peer comparison, no leaderboard, no overdue count: **Supported** as the conservative choice, consistent with the user reports above and with the carried motivation evidence (Howard et al. 2021: external regulation, meaning reward and punishment, was unrelated to performance or persistence; [Howard et al. 2021](https://doi.org/10.1177/1745691620966789), via [science_of_practice.md, carried](/docs/research/notes/Practice%20systems%20and%20learning%20science/science_of_practice.md)), though Jivet et al.'s social-comparison findings could not be retrieved.
- The same number computed in two places (Home vs end-of-session): a **demonstrated defect** in the hand test and, per one Math Academy user, a trust problem.

#### Recommendations
1. Keep the student Stats screen to views with an obvious next action: forecast, retention against target, skill map, goals and readiness, weak areas (STA-11 already ends in a one-click practice link). Log which views are opened (locally) and prune the rest.
2. Move STA-4 (and any developer-oriented comparison of policies) to a diagnostics export or a clearly labelled advanced view; keep the plain-language calibration message ("when the app says 90%, you recall about N%") if it is shown at all.
3. Compute each count once and read it from that source in Home, the summary and Stats (backlog item 5).
4. Prefer weekly and monthly aggregates for retention (Anki's own caution about daily noise) and label small samples.
5. Give every chart a text alternative (see section 7) and do not rely on colour alone in the skill map.

### Gaps
- No randomised or quasi-experimental study of a dashboard in a spaced-repetition or maths-practice tool was found; the reviews cover mostly course-level dashboards in higher education.
- Jivet et al. (2017, 2018) were retrievable only as bibliographic records; the Monash review was read through the lab's announcement rather than the paper.
- Competitor dashboards are described from vendor documentation and user posts, not studied; no usage data on which views students open was found.
- No evidence was found on how students interpret a score range versus a point estimate, or on prediction displays for self-study exam preparation.
- A study of students' perceived versus actual learning (Deslauriers et al., PNAS 2019), which would bear on whether the own-data contrast in STA-3 changes beliefs, could not be retrieved (the PMC page returned an anti-bot check).

## 5. Desktop reminders and notifications: does a reminder improve adherence, and what do macOS norms say?

### Takeaway
Randomised and company evidence shows that reminders and streak messages raise platform use, but the only large academic-outcome tests of nudging found no effect, and every source warns that over-notification costs the channel. The spec sends no system notifications (only an in-app break reminder), which fits Apple's guidance; if one reminder is added later it should be opt-in, singular, free of streak threats and measured locally.

### Cited Findings

#### Current design (spec IDs)
- [Local file] A text search of the spec and the application source found no system notification, Dock badge or menu-bar extra; the only reminder is an optional in-app break reminder every 50 minutes that "never interrupts a problem" — [spec.md, Settings table and "Long sessions"](/docs/spec.md)
- [Local file] Nudges are in-app only: Home shows the study plan again after two missed days (LIB-12), offers "Back on track by <date> at N a day" after three or more missed days (QUE-17), and never shows an overdue count (QUE-7) — [spec.md](/docs/spec.md)

#### Evidence: do reminders and nudges change use or learning?
- [RCT] Aulagnon, Cristia, Cueto & Malamud 2025, 60,000 Peruvian 4th-6th graders: messages highlighting streaks and personalised reminders with positive reinforcement "significantly increased platform use compared to generic reminders and the control group", streaks more on the intensive margin and personalised reminders more on the extensive margin; highlighting streaks also improved maths achievement versus control among the 1,500 students who took an endline test, though differences with other arms were not significant — [NBER w34173](https://www.nber.org/papers/w34173)
- [Field experiment] Oreopoulos & Petronijevic 2019, nearly 25,000 college students over five years: online and text-message interventions gave "some improvement from coaching-based interventions on mental health and study time, but none of the interventions we evaluate significantly influences academic outcomes"; students "study about five to eight hours fewer each week than they plan to, though our interventions do not alter this tendency" — [NBER w26059](https://www.nber.org/papers/w26059)
- [Company A/B or company data] Yancey & Settles (Duolingo, KDD 2020): optimising the content of millions of daily reminder notifications with a bandit algorithm "lead to a 0.5% increase in total daily active users (DAUs) and a 2% increase in new user retention over a strong baseline"; fresh templates had more impact than familiar ones — [Yancey & Settles 2020](https://research.duolingo.com/papers/yancey.kdd20.pdf)
- [Practitioner/expert opinion; company account] Mazal (Duolingo, 2023): refocusing on push notifications was one of the first big wins in turning growth around; the team could optimise timing, templates and copy but "could not increase the quantity of notifications without strong justification and CEO approval"; he warns that aggressively A/B testing emails and push notifications causes users to opt out of the channel, and "even if you kill the test, those users remain opted out forever", citing Groupon's email experience (an anecdote); a 2019 viral meme about Duolingo's "pushiness" is mentioned — [Mazal, Lenny's Newsletter](https://lennysnewsletter.com/p/how-duolingo-reignited-user-growth)
- [Field experiment, before-and-after design] Talens-Estarelles et al.: reminder software for the 20-20-20 break rule reduced digital eye strain and dry-eye symptoms during use, but the improvement "was not maintained one week after discontinuation" (a different domain, but it shows reminder effects tracking the reminder) — [Aston Research Explorer](https://research.aston.ac.uk/en/publications/the-effects-of-breaks-on-digital-eye-strain-dry-eye-and-binocular/)
- [Observational/platform data] Lally et al.: automaticity rose when a behaviour was repeated "in a consistent context", and missing one opportunity did not materially affect habit formation (the mechanism behind a fixed cue such as the LIB-12 "when and where" plan) — [Lally et al. 2010, abstract via Crossref](https://api.crossref.org/works/10.1002/ejsp.674)

#### Standards: macOS notification norms
- [Standard/guideline] Apple HIG: "Before you can send any notifications to people, you have to get their consent"; a notification should give "timely, high-value information they can understand at a glance" — [Apple HIG, Notifications](https://developer.apple.com/design/human-interface-guidelines/notifications)
- [Standard/guideline] Apple HIG: "Provide concise, informative notifications"; "Avoid sending multiple notifications for the same thing, even if someone hasn't responded … people may turn off all notifications from your app"; "Avoid sending a notification that tells people to perform specific tasks within your app … it's hard for people to remember such instructions after they dismiss the notification"; use an alert, not a notification, for an error; when the app is in the foreground, present information in a way that is "discoverable but not distracting or invasive" — [Apple HIG, Notifications](https://developer.apple.com/design/human-interface-guidelines/notifications)
- [Standard/guideline] Apple HIG: "Use a badge only to show people how many unread notifications they have" and do not use it for other numeric information; "Make sure badging isn't the only method you use to communicate essential information" because people can turn badges off; "If your notification information is critical, make sure you deliver it in other ways, too" — [Apple HIG, Notifications](https://developer.apple.com/design/human-interface-guidelines/notifications)

#### Competitor patterns
- [Company A/B or company data] Duolingo treats reminders as a core retention lever, with templates tuned by a bandit and a stated internal limit on notification volume — [Yancey & Settles 2020](https://research.duolingo.com/papers/yancey.kdd20.pdf) and [Mazal, Lenny's Newsletter](https://lennysnewsletter.com/p/how-duolingo-reignited-user-growth)

### Inferences
#### Verdicts
- No system notifications or Dock badge by default: **Weakly supported**. It matches HIG consent and restraint norms and avoids the opt-out risk, but it gives up the one lever with randomised evidence of raising use (Peru) and relies on the student to remember to open the app; LIB-12's fixed "when and where" cue is the substitute and rests on the weak evidence in section 3.
- Using a Dock badge for the number of problems due: **Unsupported by HIG** (a badge is for unread notification counts only) and at odds with QUE-7's rule against showing an overdue pile.
- Evidence that reminders improve learning outcomes: **Weakly supported**. Streak messaging raised maths scores in a 1,500-student subsample in Peru, but the largest test of nudging (Oreopoulos) found no academic effect; engagement is not the same as learning.

#### Recommendations
1. Keep system notifications off by default. If one is added, make it opt-in at the time chosen in the study plan, at most one per day, one short line ("Your set for today is ready: 20 problems, about 55 minutes"), no streak-loss or overdue wording, tapping opens Home, with an easy "skip today" and "turn off".
2. Do not show a Dock badge for due counts.
3. If a reminder ships, log locally whether a session starts within an hour of it and compare with days without one, so that the effect is measured rather than assumed.
4. Keep the break reminder in-app only.

### Gaps
- No study of desktop reminders for self-paced maths or spaced-repetition practice was found; the Peru and Duolingo findings concern children's platform use and a mobile language app.
- The NBER abstract does not state the channel (SMS, app or other) of the Peru messages.
- The Duolingo figures are company reports and the Groupon example is an anecdote in a practitioner newsletter.
- Reminder timing, wording, and frequency effects were not found for adult self-study; macOS permission flows for Python-packaged apps (native notification APIs) were not investigated beyond the HIG text.
- How Anki, Math Academy and UWorld handle desktop notifications was not verified.


## 6. macOS conventions: do the menus, shortcuts, undo, windows, theme and settings follow Apple's Human Interface Guidelines?

### Takeaway
The app follows Apple's guidance on Edit-menu Undo and Redo with the standard shortcuts, an Automatic appearance default and restoring state after a quit, and the hand test on macOS confirmed Cmd-Z, Shift-Cmd-Z and "Edit > Undo Last Answer". It departs from the guidance on an app-specific Day/Night override, 33 settings, plain-letter shortcuts, a single-level "Undo Last Answer" with no key equivalent, and no "Settings..." (Command-Comma) item; each departure has a reason, but all of this rests on Apple's guidance (expert/standard), not on empirical studies.

### Cited Findings

#### Current design (spec IDs and code)

#### Standards: Apple HIG
- [Standard/guideline] Undo and redo: "Place undo and redo commands in the Edit menu and support the standard keyboard shortcuts. Mac users expect to find undo and redo at the top of the Edit menu; they also expect to use Command-Z and Shift-Command-Z" — [Apple HIG, Undo and redo](https://developer.apple.com/design/human-interface-guidelines/undo-and-redo)
- [Standard/guideline] "Let people undo multiple times. Avoid placing unnecessary limits on the number of times people can undo or redo"; "Help people predict the results of undo and redo as much as possible … you can modify the menu item labels to identify the result"; the Edit menu guidance asks to "Clarify the target of the undo" (for example Undo Typing) — [Apple HIG, Undo and redo](https://developer.apple.com/design/human-interface-guidelines/undo-and-redo) and [Apple HIG, The menu bar](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar)
- [Standard/guideline] Custom shortcuts: "Define custom keyboard shortcuts for only the most frequently used app-specific commands … defining too many new shortcuts can make your app seem difficult to learn"; "Prefer the Command key as the main modifier key in a custom keyboard shortcut"; Shift as a secondary modifier; Option "sparingly for less-common commands or power features"; "Avoid using the Control key as a modifier"; and "don't repurpose standard keyboard shortcuts for custom actions" — [Apple HIG, Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards)
- [Standard/guideline] Settings: "Minimize the number of settings you offer. - [Standard/guideline] Appearance: "Avoid offering an app-specific appearance setting. An app-specific appearance mode option creates more work for people because they have to adjust more than one setting … they may think your app is broken because it doesn't respond to their systemwide appearance choice"; "Ensure that your app looks good in both appearance modes", including with Increase Contrast and Reduce Transparency; "no lower than 4.5:1" contrast and "strive for a contrast ratio of 7:1, especially in small text" — [Apple HIG, Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode)
- [Standard/guideline] View menu: "Provide a View menu even if your app supports only a subset of the standard view functions … if your app … does support full-screen mode, provide a View menu that includes only the Enter/Exit Full Screen menu item" — [Apple HIG, The menu bar](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar)
- [Standard/guideline] Windows and state: "The system remembers window size and placement even when an app is closed"; "Restore the previous state when your app restarts so people can continue where they left off" — [Apple HIG, Windows](https://developer.apple.com/design/human-interface-guidelines/windows) and [Apple HIG, Launching](https://developer.apple.com/design/human-interface-guidelines/launching)

#### Competitor patterns
- [Vendor docs] Anki's desktop app (also a Mac app) is driven by plain keys: Space or Enter shows the answer and then selects Good, 1-4 pick a specific button ("Many people find it convenient to answer most cards with Space and keep one finger on 1 for when they forget"), S returns to the overview or studies the selected deck, and / opens Study Deck — [Anki manual, Studying](https://docs.ankiweb.net/studying.html)

### Inferences
#### Verdicts
- Edit-menu Undo and Redo with the standard shortcuts: **Supported** by HIG, and confirmed working in the math field on the Mac.
- "Undo Last Answer" as one level, in the Edit menu, with the U key: **Weakly supported**. It matches the HIG advice to name the target of the undo, but the HIG's "avoid placing unnecessary limits" is only partly met (the spec limits it to the last answer until the next is submitted, so that scheduler state stays consistent). Two "Undo" entries in one menu (the system text Undo and Undo Last Answer) can confuse, and the U key does not work while the focus is in the answer box (shortcuts.ts), so after typing the only route is the menu or moving the focus.
- Plain-letter shortcuts (H, G, E, D, R, P, U, F, Space, 1-5): **Weakly supported**. They depart from the HIG preference for Command-based custom shortcuts and from "too many shortcuts", but they follow the convention of the closest comparator (Anki) and the spec's rule that every action has a key; they also create the WCAG 2.1.4 issue in section 7.
- App-specific Day/Night override: **Weakly supported**. The HIG advises against an app-specific appearance setting; mitigated because Automatic is the default and follows the system setting, but a student who picks Day while the Mac is dark is exactly the case the HIG describes. The spec's reason is reading comfort (see section 8).
- 33 settings: **Weakly supported / at risk**. The HIG says minimise settings; many of these are scheduling parameters that may be better as defaults with an "Advanced" group.
- No "Settings…" (Command-Comma) item: **Missing** (because the app has no custom app menu, and Settings is a sidebar page); easy to add and expected by Mac users.
- Focus mode full screen without a View menu item: **Missing / unchecked** (whether pywebview's default menu bar offers Enter Full Screen was not verified).

#### Recommendations
1. Add a Settings… item (Command-Comma) to the app menu that opens the Settings page, and an Enter/Exit Full Screen item in a View menu that also drives Focus mode.
2. Add a key equivalent for Undo Last Answer that works from the answer box (a Command-modified shortcut that does not collide with the HIG's standard shortcut table, since plain Command-Z already undoes typing), and label the menu item with its target (for example "Undo Last Answer (Problem 7)") when it is enabled; disable it otherwise.
3. Group the 33 settings into a short default view and an Advanced group; remove any that are not needed for a single-user first release.
4. Keep Automatic as the default and make the Day/Night choice read as an override of the system ("Match system" / "Always Day" / "Always Night").
5. Finish the unchecked hand-test items (paste, dead keys, alert sound) because they affect whether Edit-menu behaviour is correct for typing in the math field.

### Gaps
- Apple's HIG is guidance from the platform vendor, not an empirical study; no usability data exists here on how Mac users react to plain-letter shortcuts in study tools.
- Whether pywebview's default menu includes a View menu with Enter Full Screen, and whether the window position and size are restored between launches, was not checked.
- How the page's Command-Z interacts with MathLive's own undo stack (beyond the hand-test result that it works) was not studied; MathLive's issue tracker could not be read (GitHub fetches were blocked).

## 7. Accessibility of math and the interface: how well do MathML, KaTeX, MathLive and the WCAG 2.2 AA target support screen-reader, keyboard and low-vision users?

### Takeaway
KaTeX's default MathML output and MathLive's speech support give a plausible but untested path for VoiceOver, and the plain-text answer mode is a sound fallback. The spec's WCAG 2.2 AA claim is not met on four points that can be checked from the files: single-key shortcuts cannot be turned off or remapped (2.1.4, Level A), the text-size slider reaches only about 156% of the default (1.4.4 and the HIG's 200%), several colour pairs and the input border fall below contrast thresholds, and charts have no stated text alternatives; a VoiceOver pass in the real WKWebView (DEV-15) is the decisive missing evidence.

### Cited Findings

#### Current design (spec IDs and code)
- [Local file] Spec "Accessibility": every action has a key with visible focus rings; text size runs from 14 to 28 px with math scaling with it; "KaTeX's MathML output lets screen readers read the math; every button has a label"; macOS Increase Contrast is respected; focus is never hidden (WCAG 2.2 Focus Not Obscured); targets are at least 24 by 24 px; verdicts are announced through a live region — [spec.md, "Accessibility"](/docs/spec.md)
- [Local file] DEV-15: "A keyboard-only script has no pointer-only step; the app meets WCAG 2.2 AA, including Focus Not Obscured (2.4.11), 24-px targets (2.5.8) and verdicts in a live region; a VoiceOver pass covers sample math" — [spec.md DEV-15](/docs/spec.md)
- [Local file] Problem text math is rendered with `output: 'htmlAndMathml'`; the preview uses KaTeX with its default output; a start-up self-test fails if the rendered formula has no `.katex-mathml math` node — [web/src/lib/markdown.ts](/web/src/lib/markdown.ts), [web/src/components/Tex.svelte](/web/src/components/Tex.svelte), [web/src/lib/selftest.ts](/web/src/lib/selftest.ts)

- The accent focus ring is 4.85:1 (Day) and 7.15:1 (Night) against the page, so focus indication passes; on-accent button text is 5.16:1 and 7.15:1.
- Correct (teal) and incorrect (orange) have almost the same luminance (1.03:1 in Day, 1.09:1 in Night), so they cannot be told apart by lightness; the icon-plus-word design in VerdictBadge is therefore essential rather than decorative.
- Most Day pairs are below the HIG's "strive for 7:1" (muted 5.6 to 6.0, accent 4.9 to 5.2, correct 4.6 to 4.9, incorrect 4.5 to 4.8, warning 4.3 to 4.5); the spec's own bar is WCAG AA, which they meet on the surface colour but not always elsewhere.

#### Verdicts
- Math in screen readers via KaTeX MathML: **Weakly supported**. The mechanism is documented (htmlAndMathml default; VoiceOver reads native MathML well in Safari per one practitioner test; the app's self-test confirms the MathML node exists), but no source tests KaTeX's hidden MathML inside a pywebview WKWebView, and the DEV-15 VoiceOver pass has not yet been run.
- MathLive as an accessible input: **Weakly supported**. MathLive documents speech output (OS text-to-speech, offline) and ARIA labels, but those are vendor claims; no independent evaluation or screen-reader test was found. The plain-text answer mode (a labelled input) is a sound fallback; the toggle is reachable by the ` key.
- WCAG 2.1.4 Character Key Shortcuts: **Not met as specified**. The single-key shortcuts (H, G, E, D, R, P, U, F, Space, 1-5) are global to the page when the focus is outside a text field (so not "active only on focus"), and the Settings table has no way to turn them off or remap them. Level A, and the failure particularly affects Voice Control or Dragon dictation users. Enter, Shift+Enter and Esc are non-printing keys and fall outside this criterion; the backtick (`) mode toggle is a symbol-character shortcut that stays active inside the answer box, which can be argued as "active only on focus" of that component but should still be remappable.
- WCAG 1.4.4 and HIG 200% text: **Not met as specified**. The slider ends at 28 px, which is 155.6% of the 18 px default (200% only relative to the 14 px minimum); no page-zoom is described.
- WCAG 1.4.3 and 1.4.11 contrast: **Partly met**. Every pair in the test's list passes by my arithmetic (the lowest is Day warning on surface at 4.52); but Day warning (4.26) and incorrect (4.496) fall short on the page background, and accent, correct, incorrect and warning fall short on the selection colour in Day, and incorrect falls short on the selection colour in Night; the test enumerates pairs by hand, so a text colour placed on an unlisted background is not caught; the input border is a non-text contrast gap.
- WCAG 4.1.3 live regions: **Weakly supported**. Verdicts are announced; the preview region is also `aria-live="polite"` and updates as the student types, which may be chatty; this needs a screen-reader test.
- WCAG 2.2.1 Timing Adjustable: **Supported for ordinary practice** by the Untimed switch (TIME-6) and silent timing; the timed practice tests (QUE-18) are time-limited by design and the spec describes no timing accommodation for them (the carried notes record Math Academy's Accommodations setting relaxing quiz timing).
- Reduced motion and Increase Contrast: **Supported / partly supported**. Reduced motion zeroes the transitions (WCAG 2.3.3 and HIG); Increase Contrast changes only border and focus width, not text colours.
- Colour not the only signal (WCAG 1.4.1, HIG): **Supported** for verdicts (icon plus word plus colour).
- Text alternatives for charts (WCAG 1.1.1): **Missing** in the spec; the forecast, retention, calibration, time and speed views (STA-2, STA-3, STA-4, STA-7, STA-9) are charts and the skill map (STA-5) is a heatmap, with no text alternative stated.

#### Recommendations
1. Run the DEV-15 VoiceOver pass first on the real WKWebView build: read a problem with a fraction and a root, enter an answer in the math field with and without VoiceOver, read the preview and verdict, and tab out of the math field (no trap, 2.1.2). Also test Voice Control and Full Keyboard Access.
2. Add a setting "Single-key shortcuts: On/Off" (Off keeping Enter, Esc and menu commands) or make letter shortcuts active only when a button has focus; this resolves 2.1.4.
3. Extend text size to at least 200% of the default (for example up to 36 px) and test text spacing (1.4.12) and reflow at the largest size.
4. Compute colour pairs from the rendered styles (an automated checker such as axe) instead of a hand list; darken Day warning and incorrect slightly so they pass on every background and on selection, and give inputs a border or background that meets 3:1 without needing Increase Contrast.
5. Provide a text summary or table behind each chart and keep colour-plus-icon in the skill map.
6. Consider the MathJax Explorer-style keyboard navigation for the worked solutions only if VoiceOver proves inadequate on KaTeX's output; in the meantime ensure each solution step is a separate text block.

### Gaps
- No independent test of VoiceOver with KaTeX output in WKWebView, or with MathLive's math-field in WKWebView, was found; the MathLive accessibility guide page was not found and GitHub issue trackers (MathLive, KaTeX) could not be read.
- The W3C gap analysis is from 2021 and the HTMHell test is one author's, using native MathML in Safari; neither covers KaTeX's visually hidden MathML.
- Contrast figures are my own arithmetic from the spec palette; whether a given component places incorrect or warning text on the page background or on a panel was not traced beyond the grep of usage sites.
- Whether macOS Increase Contrast maps to `prefers-contrast: more` inside pywebview's WKWebView, and whether pywebview exposes page zoom, was not tested.
- No data was found on how many students use screen readers, switch control or dictation with maths tools; the recommendations are standards-based.


## 8. Typography, layout and the visual design of feedback: what supports Day/Night polarity, the colour palette, type choices, dyslexia options, sound and worked solutions?

### Takeaway
Most visual choices are consistent with accessibility guidance and with the feedback literature (explanations beat correctness-only feedback, especially in maths), but three specific spec claims have no source I could retrieve: that avoiding pure white and black at 13 to 15:1 "cuts glare", that teal and orange can be told apart by colour-blind readers (the two colours have almost identical lightness), and that a serif face suits maths. Dyslexia-specific fonts showed no benefit in the studies found, while extra letter spacing did help children with dyslexia.

### Cited Findings

#### Current design (spec)
- [Local file] "Design and theme": Day, Night and Automatic (default); "Dark text on a light background reads better in a lit room, with better proofreading and smaller pupils in studies by Piepenbrock and colleagues (2013 and 2014). A dark screen in a dark room avoids glare"; three rules: no pure white or black ("Contrast stays high but not maximal, about 13 to 15 to 1, which cuts glare and the halo some readers see around bright text on black"), one accent colour, and colour never the only signal ("Correct and incorrect use teal and orange, which color-blind readers can tell apart, plus a check or cross and a word") — [spec.md, "Design and theme"](/docs/spec.md)
- [Local file] Type: Source Serif 4 for problem text ("sits naturally beside KaTeX's math"), Inter for the interface, 18 px with 1.6 line height in a column of about 70 characters, math at 1.05 times the text size, tabular numbers in Stats; one centred column on the study screen; fades of 150 ms or less, no sounds by default, the OS reduce-motion setting respected — [spec.md](/docs/spec.md) and [tokens.css](/web/src/styles/tokens.css)
- [Local file] Verdict display: each verdict is an icon plus a word plus colour ("Correct", "Incorrect", "Not quite" on a first miss, "Check your answer" for an unparseable answer), semi-bold at 18 px; the first wrong attempt shows "Not quite" and nothing else; a worked solution follows the final attempt — [VerdictBadge.svelte](/web/src/components/VerdictBadge.svelte) and [spec.md, "Answering"](/docs/spec.md)
- [Local file] The project's spike script lists "Typing does not play the macOS alert sound (pywebview #1722)" as a check, and the hand test lists the alert sound as not yet checked by hand — [scripts/spike_measure.py](/scripts/spike_measure.py) and [backlog.md](/docs/backlog.md)

#### Evidence: polarity, contrast and glare
- [Lab study] Piepenbrock, Mayr & Buchner (Human Factors): in a proofreading task with black text on white versus white text on black at four sizes (8, 10, 12 and 14 pt), "a positive polarity advantage was observed in proofreading performance" and it "linearly increased with decreasing character size"; the authors attribute it to the higher luminance of positive-polarity displays aiding perception of detail — [Piepenbrock et al., abstract via Crossref](https://api.crossref.org/works/10.1177/0018720813515509)
- [Standard/guideline] Apple HIG: for custom colours "strive for a contrast ratio of 7:1, especially in small text", and warns that "in Dark Mode with Increase Contrast … dark text is less legible when it's on a dark background" for some combinations — [Apple HIG, Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode)

#### Evidence: type, layout and reading options
- [Standard/guideline] WCAG 1.4.8 Visual Presentation (Level AAA, beyond the app's AA target): a mechanism for the user to choose foreground and background colours; width no more than 80 characters; text not justified; line spacing at least 1.5 within paragraphs and paragraph spacing at least 1.5 times the line spacing; text resizable to 200% without horizontal scrolling — [WCAG 1.4.8](https://www.w3.org/WAI/WCAG22/Understanding/visual-presentation.html)
- [Standard/guideline] Apple HIG for macOS: Body text style 13 pt (minimum 10 pt in the specifications table), and "macOS doesn't support Dynamic Type" — [Apple HIG, Typography](https://developer.apple.com/design/human-interface-guidelines/typography)
- [Lab study, single-subject design] Wery & Diliberto: in 12 elementary students with dyslexia (11 completing every probe), the OpenDyslexic font gave "no improvement in reading rate or accuracy" compared with Arial and Times New Roman, and "none of the participants reported preferring to read material presented in that font" — [Wery & Diliberto, Annals of Dyslexia, PMC5629233](https://pmc.ncbi.nlm.nih.gov/articles/PMC5629233)
- [Lab study; title only] A further study is titled "Dyslexie font does not benefit reading in children with or without dyslexia" (Kuster et al. 2017, Annals of Dyslexia); only the title was retrievable — [Kuster et al. 2017, record via Crossref](https://api.crossref.org/works/10.1007/s11881-017-0154-6)
- [Lab study] Zorzi et al. 2012: "a simple manipulation of letter spacing substantially improved text reading performance on the fly (without any training) in a large, unselected sample of Italian and French dyslexic children"; the authors explain it as reduced crowding — [Zorzi et al., PNAS, abstract via Crossref](https://api.crossref.org/works/10.1073/pnas.1205566109)

#### Evidence: feedback content, colour and sound
- [Meta-analysis/review] van der Kleij, Feskens & Eggen 2015: from 40 studies and 70 effect sizes of item-based feedback in computer-based environments, elaborated feedback (for example an explanation) gave a mean effect of 0.49, against 0.05 for knowledge of result (correct or not) and 0.32 for knowledge of the correct response; elaborated feedback was especially better for higher-order outcomes; "larger effect sizes were found for mathematics compared with social sciences, science, and languages"; delayed feedback had a negative effect; no significant interaction between timing and type of learning — [van der Kleij et al., Review of Educational Research, via Crossref](https://api.crossref.org/works/10.3102/0034654314564881)
- [Meta-analysis/review] Shute 2008: according to researchers, formative feedback "should be nonevaluative, supportive, timely, and specific", with types ranging from verification of accuracy to explanation, hints and worked examples — [Shute, Review of Educational Research, via Crossref](https://api.crossref.org/works/10.3102/0034654307313795)
- [Standard/guideline] Apple HIG: "Make sure all feedback is accessible … when you provide feedback using color, text, sound, and haptics, people can receive it whether they silence their device, look away from the screen, or use VoiceOver"; and "Make motion optional … avoid using it as the only way to communicate important information" — [Apple HIG, Feedback](https://developer.apple.com/design/human-interface-guidelines/feedback) and [Apple HIG, Motion](https://developer.apple.com/design/human-interface-guidelines/motion)
- [Standard/guideline] Apple HIG lists blue-orange and red-green as pairings that "people who are color blind may have particular difficulty with", and asks for "distinct shapes or icons, in addition to color" — [Apple HIG, Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- [Meta-analysis/review; title only] Attali & van der Kleij 2017 ("Effects of Feedback Elaboration and Feedback Timing During Computer-Based Practice in Mathematics Problem Solving", Computers & Education 110) is directly relevant to first-miss versus elaborated feedback, but only the bibliographic record was retrievable — [ETS record](https://www.ets.org/research/policy_research_reports/publications/article/2017/jxqf.html)

#### Competitor patterns
- [Vendor docs; carried] UWorld presents rationales as "the most important part" of a question, and Math Academy gives an explanation for every question and encourages checking wrong answers against worked solutions — [practice_platforms.md section 7, carried](/docs/research/notes/Practice%20systems%20and%20learning%20science/practice_platforms.md) and [prior_art_and_ux.md section 6, carried](/docs/research/notes/Toishi%20build%20research/prior_art_and_ux.md)

### Inferences
#### Verdicts
- Day (dark on light) for lit rooms, Automatic by default: **Weakly supported**. Piepenbrock's proofreading result favours dark-on-light, and by its own finding the advantage shrinks as characters get larger, so it should be smallest for 18 px problem text; it used pure black and white, not the off-white palette. The Night theme for dark rooms rests on the spec's glare rationale, for which no source was retrieved, and on system convention (HIG).
- "About 13 to 15:1 cuts glare and halo": **Unsupported** (no source retrieved). The Day text pairs measure 14.6 and 15.5:1, the Night pairs 12.2 and 13.5:1 (my arithmetic, section 7), so the quoted range is approximately accurate but not a tested optimum.
- Source Serif 4 and Inter, 18 px, 1.6 line height, about 70 characters, left-aligned single column: **Weakly supported**. It is consistent with WCAG 1.4.8's AAA guidance (at most 80 characters, at least 1.5 spacing), but no study of serif versus sans-serif type for maths text was found.
- No dyslexia-specific font: **Supported** (no benefit found in the studies retrieved). A reading option for letter spacing and line spacing is **Missing**: Zorzi supports extra letter spacing for children with dyslexia, but adult and maths-text effects are untested.
- Teal and orange with icon and word, never colour alone: **Supported** as a redundancy design (WCAG 1.4.1, HIG). The spec's claim that colour-blind readers "can tell apart" teal and orange is **Unsupported**: the two colours have luminance ratios of 1.03:1 (Day) and 1.09:1 (Night), so only hue separates them, and the HIG names blue-orange as a risky pairing (the app's accent is blue and the incorrect colour orange). The icon and word make this harmless for verdicts; the skill map (STA-5) and the correct/incorrect marks in lists need the same redundancy.
- A worked solution after every final attempt: **Supported**. Elaborated feedback has the largest mean effect in the maths-heavy meta-analysis (0.49 versus 0.05 for correctness only); competitors present explanations as central.
- First miss shows only "Not quite": **Weakly supported / untested**. Correctness-only feedback had the smallest effect (0.05), but the design deliberately withholds the answer to elicit a second attempt, and the explanation appears after the last attempt, so it is not delayed feedback in the meta-analysis sense; the trade-off is untested here.
- No sounds by default, motion optional and short: **Supported** by HIG and WCAG 2.3.3; the unverified risk is the macOS alert beep on unhandled key presses.

#### Recommendations
1. Keep Automatic as the default and word the Day/Night options as overrides ("Always light", "Always dark").
2. Remove "cuts glare and the halo" from the spec text unless a source is found, and either cite the specific Piepenbrock paper behind "smaller pupils" or drop the phrase (the only Piepenbrock abstract retrieved here attributes the advantage to higher display luminance and does not mention pupils; the other 2013 paper was not identified, so the phrase may be sourced there); keep the 12 to 15:1 range as a design choice, not a finding.
3. Run a colour-vision-deficiency simulation on the verdict badges, the skill map and any chart; give each skill-map state a shape or pattern as well as a colour.
4. Add an optional "Reading" group in Settings with letter spacing and line spacing steps (consistent with WCAG 1.4.12) instead of a dyslexia font.
5. Finish the hand check of the macOS alert sound on keys outside text fields and Space/Enter handling.
6. Log how often a first "Not quite" is followed by a corrected second attempt, and consider a one-line nudge for common known-wrong forms if the correction rate is low.

### Gaps
- No source was retrieved for the glare statement, and none for "smaller pupils" beyond the spec's own attribution to Piepenbrock and colleagues (the only abstract retrieved says nothing about pupils, so the claim is unverified rather than shown wrong); the other 2013 or 2014 Piepenbrock paper could not be identified (a guessed DOI returned an unrelated paper), and the Legge and Bigelow print-size review was not retrievable (Crossref had no abstract).
- No study of serif versus sans-serif type for maths text, of off-white versus white backgrounds for symbolic work, or of Night-theme reading performance in a dark room was found.
- The Zorzi study is of children; Wery & Diliberto had 12 students; the Kuster result was seen as a title only.
- The effect of withholding the answer on a first miss, versus a hint, was not found (Attali and van der Kleij 2017 would be the first paper to read).
- Colour-vision simulation of the palette was not run here.

## 9. Overall: which UI decisions are supported by evidence, and what should change first?

### Takeaway
The answer input and accessibility conformance hold the largest risks and the cheapest fixes (a shortcut toggle, contrast and text size, a VoiceOver test); the session-design and onboarding choices are reasonable but rest on weak or indirect evidence; and nothing supports dashboards raising achievement, so the Stats screen should stay small and its numbers consistent. Several spec claims should be softened where the evidence is mixed (LIB-12) or missing (glare, colour-blind distinguishability).

### Cited Findings
These are the strongest anchors from sections 1 to 8, repeated so that the report can use them without cross-reading.
- [Practitioner/expert opinion] STACK's design rule is to reject unparseable input as "invalid" "to stop students being penalized on a technicality", with a two-step validation that echoes the student's input back — [STACK docs, Inputs](https://docs.stack-assessment.org/en/Authoring/Inputs)
- [Observational/platform data] Isaac Physics survey (563 valid respondents): 76.1% tend to avoid symbolic questions and 76.0% do not enjoy the equation editor — [Franceschini et al., L@S 2019](https://www.cl.cam.ac.uk/~arb33/papers/FranceschiniSharkeyBeresford-InequalityWebEquationEntry-LearningAtScale2019.pdf)
- [Meta-analysis/review] Micro-breaks: vigor d = .36 and fatigue d = .35 but no significant effect on performance (d = .16) — [Albulescu et al. 2022](https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0272460)
- [Field experiment] Task-based goals "had large and robust positive effects on the level of task completion" and raised course performance — [Clark et al. 2017](https://www.nber.org/papers/w23638)
- [Field experiment, preregistered] Plan-making prompts' large effect did not replicate across 247 courses and 269,169 students — [Kizilcec et al. 2020](https://pmc.ncbi.nlm.nih.gov/articles/PMC7334459)
- [Meta-analysis/review] Learning-analytics dashboards: "no evidence to support the conclusion that LADs have lived up to the promise of improving academic achievement", but substantial effects on participation — [Kaliisa et al. 2024](https://arxiv.org/abs/2312.15042)
- [RCT] Streak-highlighting messages raised platform use (60,000 Peruvian students); nudging college students had no effect on academic outcomes (nearly 25,000) — [NBER w34173](https://www.nber.org/papers/w34173) and [NBER w26059](https://www.nber.org/papers/w26059)
- [Standard/guideline] WCAG 2.1.4 Character Key Shortcuts (Level A) requires turn-off, remap or active-only-on-focus for single-key shortcuts — [W3C Understanding 2.1.4](https://www.w3.org/WAI/WCAG22/Understanding/character-key-shortcuts.html)
- [Standard/guideline] Apple HIG: postpone nonessential setup, minimise settings, place Undo and Redo in the Edit menu with Command-Z and Shift-Command-Z, avoid app-specific appearance settings — [Onboarding](https://developer.apple.com/design/human-interface-guidelines/onboarding), [Settings](https://developer.apple.com/design/human-interface-guidelines/settings), [Undo and redo](https://developer.apple.com/design/human-interface-guidelines/undo-and-redo), [Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode)
- [Meta-analysis/review] Elaborated feedback mean effect 0.49 versus 0.05 for knowledge of result, larger for mathematics — [van der Kleij et al. 2015](https://api.crossref.org/works/10.3102/0034654314564881)

#### Prioritised recommendations
1. Test the answer input first, on the real build, with VoiceOver, Voice Control, Full Keyboard Access, dead keys, an IME or non-US layout, and paste (DEV-15 plus the open backlog items); log first-attempt invalid rate by answer type from day one.
2. Fix WCAG 2.1.4 (a Single-key shortcuts On/Off setting, or letter shortcuts active only when a control has focus). It is a Level A criterion and a cheap change.
3. Fix contrast and size: darken Day warning and incorrect, check the selection colour, give input boundaries 3:1 without relying on Increase Contrast, extend text size to at least 200% of default, add text alternatives for charts, and replace the hand-enumerated contrast pairs with a rendered-style check.
4. Rework first run: put the input tutorial before the placement test, make it skippable and re-openable, drop the theme question, postpone the study-plan prompt to after the first session, and soften the LIB-12 sentence to "evidence on planning prompts is mixed".
5. Keep the student Stats screen small, move STA-4 to a diagnostics view, and compute each count once so that Home, the summary and Stats cannot disagree.
6. Align with macOS: add Settings… (Command-Comma) and a View menu with Enter Full Screen, add a key equivalent for Undo Last Answer that works from the answer box, and group the 33 settings.
7. Keep system notifications off by default; if a reminder is added, make it opt-in, once a day, free of streak threats, and measure its effect locally.
8. Treat the break reminder, streak and freeze rules and Lighter-set rules as tunable defaults and log how they are used.
9. Remove or source the "cuts glare" and "colour-blind readers can tell apart" statements in the spec (and verify the "smaller pupils" attribution to Piepenbrock, which I could not confirm), run a colour-vision simulation, and offer a reading option for letter and line spacing.
10. Add a local-only instrumentation plan so that the questions the literature cannot answer (invalid rate by answer type, first-run time and drop-off, which Stats views are opened, reminder responsiveness, first-miss correction rate) are answered by the app's own logs.
